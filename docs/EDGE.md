# Edge-узел на стенде LinQ: запуск, проверка, цифры

Владелец — A10 edge-deploy. Решение D-005 (`.orchestra/DECISIONS.md`): конвейер распознавания работает в Jupyter-контейнере стенда рядом с LinQ TPU, а ноутбук (gateway, A3) принимает события и показывает UI. Код edge — `guard/edge.py` (основа A3), конфиги — `configs/cameras.stand.yaml` и `configs/models.stand.yaml`, замеры — `guard/edge_probe.py`, сырые цифры — `.orchestra/metrics/edge-*.json`.

**Итог замера 24.10 10:02 МСК (300 с, 4 камеры, настоящий TPU):**
- каждая камера анализируется с частотой **4.8–4.9 к/с** (цель 5);
- CPU контейнера — **1.18 из 1.5 ядра**;
- сквозная задержка оповещения от первого нарушающего кадра до получения на ноутбуке — **p50 2.20 с, p95 2.53 с**. Из них 1.7 с — окно подтверждения правила (`min_duration_s`), остальное — **0.31 с** (p50) от кадра подтверждения до ноутбука;
- `frame_meta` теряется **0.02 %**, доходит за p50 0.32 с.

## 1. Схема

```
Jupyter-контейнер стенда (1.5 CPU, 4 ГиБ)                                  Ноутбук
 ┌────────────────────────────────────────────────────────────────────┐
 │ 4 × FileSource 640×360, 25 к/с → выборка 5 к/с                    │
 │   → letterbox → RawCodec (int8) ─► RabbitMQ tpu.direct ─► LinQ TPU │
 │   ◄─ выходы головы ─ хвост ONNX (DFL) → декод + NMS → ByteTrack    │
 │   → правила → EventManager → EdgeSink ─► exchange zazerkalye ──────┼──► очередь zazerkalye.gateway
 └────────────────────────────────────────────────────────────────────┘      (VPN-контейнер, 127.0.0.1:5672)
                                                                             → gateway (A3): журнал, WS, UI
```

- Брокер для TPU и для нашего канала один и тот же — `10.0.114.30:5672`. Со стенда RTT 1 мс, с ноутбука через VPN — 225 мс.
- Модели: det и pose — YOLOv8n 480, ppe (YOLOv8s) и fire — 640. Все на TPU, программы O5, raw-режим (`docs/LINQ_NOTES.md` §13–16).
- Камеры `cam_s1`…`cam_s4` — те же, что в демо A3 (`configs/cameras.yaml`): ролики s1_01 (зона), s2_01 (СИЗ), s3_02 (падение), s4_02 (техника). Зоны и правила совпадают, поэтому gateway показывает камеры по своему конфигу. Проверяет это `tests/test_edge_stand.py`.

Всё выполняется с ноутбука через VPN-контейнер (`infra/vpn/vpnctl.sh status` → UP), Python — с `unset PYTHONPATH`.

   - Воркер TPU читает программы из `/auto/cache/hackathon10864/`.
   - Программы `ppe_640` и `fire_640` A2 собрала, но в кэш не выложила. A10 скопировал их 24.10 09:32; `ppe_640s1` и `fire_640s1` A2 выложила сама.
3. **Код:** `python tools/stand.py sync` — архивом, только изменения, в `~/work/mosprom`.
4. **Ролики** и субпоток для анализа:
   ```bash
   python tools/stand.py --root /Users/nagimov-timur/Desktop/mosprom sync-data --videos s1_01,s2_01,s3_02,s4_02
   JUPYTER_URL=http://127.0.0.1:8888 python tools/jhub.py sh 'cd ~/work/mosprom && mkdir -p data_360/videos && \
     for v in s1_01 s2_01 s3_02 s4_02; do ffmpeg -nostdin -loglevel error -y -threads 2 -i data/videos/$v.mp4 \

   ```
   - `--root` указывает на основной checkout: `data/` в worktree нет.
   - Субпоток 640×360 сохраняет 25 к/с и число кадров. Поэтому `frame_idx` (позиция в файле), по которому gateway синхронизирует свой ролик 1280×720, совпадает, а рамки gateway масштабирует по `w/h` из `frame_meta`.

## 3. Запуск, проверка, остановка

Демо одной командой — `scripts/run_tpu.sh`: VPN-контейнер → edge на стенде (если не запущен; `SYNC=1` — залить код и перезапустить) → очистка `zazerkalye.gateway` от накопленного без шлюза → шлюз с UI на `127.0.0.1:8000`. Остановка шлюза — Ctrl+C, edge на стенде — `python tools/stand.py stop`.

```bash
python tools/stand.py start          # ~/guard311/bin/python -m guard.edge --config configs/cameras.stand.yaml
python tools/stand.py status         # PID, RSS, CPU и хвост лога
python tools/stand.py logs -n 100    # раз в 10 с строка "stats: fps … | cpu ctr … | sent … | gw consumers …"
python tools/stand.py health         # hub, сервер, процесс, очередь
python tools/stand.py stop           # SIGTERM группе процессов; edge дожидается отправки и пишет сводку "edge stopped: {…}"
python tools/stand.py restart        # stop + start
```

- `start` запускается с `OMP_NUM_THREADS=2` и `GUARD_BACKEND=linq-tpu`. Остальное edge берёт из секции `edge:` файла камер: реестр `configs/models.stand.yaml`, `~/work/models`, `~/work/mosprom/data_360`, брокер стенда, raw, окно 4.
- Приоритет настроек: флаги CLI > переменные `GUARD_*` > секция `edge:` > значения по умолчанию.
- Прогон на CPU того же контейнера (для сравнения):
  ```bash
  python tools/stand.py restart --cmd "exec ~/guard311/bin/python -m guard.edge --config configs/cameras.stand.yaml --backend onnx-cpu"
  ```
- Проверка без брокера, лог вместо транспорта: `~/guard311/bin/python -m guard.edge --config configs/cameras.stand.yaml --transport log --duration 45`.

**Проверка с ноутбука** — замеряющий подписчик:

```bash
python -m guard.edge_probe --duration 300 --out .orchestra/metrics/edge-tpu-$(date +%Y%m%d-%H%M).json
```

- Подписчик читает `zazerkalye.gateway` через `127.0.0.1:5672` и печатает сводку (события, задержки, потери, часы).
- **Если шлюз работает, замер запускать только с `--tap`.** У общей очереди брокер раздаёт сообщения потребителям по очереди: шлюз недосчитывается половины `event`, создаёт событие из `event_update` уже без снапшота и с опозданием на 6–14 с (так было 24.10 12:34–12:44, когда замер стабильности шёл параллельно с демо). `--tap` читает копию потока через свою временную очередь на тех же ключах и шлюзу не мешает. Без `--tap` подписчик предупреждает о чужом потребителе (`consumers_before`).
- `--prefetch 1 --ack-every 1` воспроизводит поведение `RabbitSource` шлюза (§7.1).

## 4. Что публикует edge

| Сообщение | Когда | Содержимое | Размер |
|---|---|---|---|
| `event` | событие подтверждено | Event + снапшот JPEG (≤ 640 px, q≈70, ≤ 60 КБ). В `details.edge`: `node` и `sent_at` (epoch по часам стенда в момент передачи в транспорт) | ~25 КБ |
| `event_update` | событие закрыто или изменено | Event без снапшота | ~0.8 КБ |
| `frame_meta` | каждый обработанный кадр | `camera_id`, `frame_idx` (позиция в файле), `ts`, рамки людей и объектов с ID трека, нарушители. Флаги: бит 0 — нарушитель | ~150 Б |
| `metrics` | раз в 2 с | как `/api/metrics` + ключ `edge` (ниже) | ~6 КБ |
| `heartbeat` | раз в 2 с | `node_id`, `ts` | ~70 Б |

`metrics.edge`:
- `cpu` — `container_cores`, `container_pct_of_limit` (cgroup v2: `cpu.stat`, `cpu.max`), `process_cores`;
- `memory`;
- `clock` — сдвиг часов стенда по NTP, `offset_ms` и `uncertainty_ms`;
- `transport` — отправлено по видам и камерам, задержано защитой канала, вытеснено из очереди отправки, состояние очереди шлюза;
- `frames_processed` по камерам, `events_created`, `uptime_s`.

### Защита канала (`gateway_guard`)

Очередь `zazerkalye.gateway` одна на все виды сообщений. У событий и метрик нет TTL. TTL `frame_meta` (10 с) RabbitMQ применяет только к голове очереди, а событие в голове TTL не имеет. Без потребителя очередь за ~100 с дорастает до `x-max-length` = 2000, брокер начинает отклонять публикации (`reject-publish`), и канал встаёт. Когда gateway подключится, ему придётся разбирать тысячи устаревших сообщений.

Поэтому edge раз в 2 с смотрит очередь (passive declare по отдельному соединению):
- нет потребителя — не шлёт `frame_meta` и `metrics`, а `heartbeat` шлёт раз в 30 с;
- в очереди больше 300 сообщений — приостанавливает `frame_meta`, возобновляет ниже 150;
- события отправляются всегда.

В метриках это видно как `transport.held_by_guard` и `gateway_queue`. Отключение — `--no-gateway-guard` или `gateway_guard: {enabled: false}`.

## 5. Методика замеров

- **Подписчик:** `guard/edge_probe.py` на ноутбуке, `prefetch` 200 и групповой ack. При таком режиме потребитель не ограничивает канал (о `prefetch` 1 — §7.1).
- **Часы.** У стенда и ноутбука разные часы: стенд отстаёт от NTP на **3.66 с**, ноутбук — на 0.33 с. Разность D = часы ноутбука − часы стенда оценивается двумя способами:
  - по NTP: edge публикует свой сдвиг в `metrics.edge.clock` (pool.ntp.org, RTT 4 мс), подписчик меряет свой (RTT 222 мс);
  - по RTT: min(t_получения − ts heartbeat/metrics) − RTT_min/2 по 294 сообщениям, RTT_min ноутбук ↔ брокер = 224.6 мс.
  
  Результаты: 3335.1 и 3334.0 мс, расхождение **1.1 мс**. Формальная погрешность каждого способа — ±112 мс (RTT/2 ноутбука), но совпадение двух независимых оценок говорит о реальной точности в единицы миллисекунд.
- **Сквозная задержка оповещения** = t_получения на ноутбуке − D − `Event.started_at` (захват первого нарушающего кадра на стенде). Разложение:
  - окно подтверждения `confirmed_at − started_at`;
  - edge: от кадра подтверждения до передачи в транспорт, `sent_at − confirmed_at` (ожидание кадра в слоте, конвейер, снапшот);
  - канал `t_получения − D − sent_at`.
- События, ушедшие с edge до подключения подписчика (`sent_at` раньше начала приёма), из задержек исключены: они ждали в очереди. В отчёте это `backlog_excluded`.
- **Потери `frame_meta`** = 1 − полученные / прирост `frames_processed` за окно между первой и последней метрикой. Каждый обработанный кадр даёт один `frame_meta`.

## 7. Проблемы и ограничения

### 7.1. Шлюз брал сообщения по одному (`RabbitSource`, prefetch 1) — исправлено в 79a8920 (`CONSUMER_PREFETCH = 200`)

`guard/transport/rabbit.py::_connect` для потребителя вызывает `basic_qos(prefetch_count=1)` и подтверждает каждое сообщение отдельно. Брокер отдаёт следующее сообщение только после ack, поэтому через VPN (RTT 225 мс) потребитель берёт не больше ~4 сообщений/с. Edge шлёт 20.7 сообщения/с. Замер `.orchestra/metrics/edge-tpu-prefetch1-20261024-1009.json` (150 с, `--prefetch 1 --ack-every 1`, тот же edge на TPU):

| | prefetch 200 (§6.1) | prefetch 1, как в шлюзе |
|---|---|---|
| принято сообщений/с | 20.7 | **3.5** |
| сквозная задержка оповещения p50 / p95, с | 2.20 / 2.53 | **12.64 / 12.92** |
| канал стенд → ноутбук p50, с | 0.15 | **10.45** |
| `frame_meta`: задержка p50, с / потери | 0.32 / 0.02 % | **10.24 / 93.5 %** |

- Голову очереди держат `frame_meta` с TTL 10 с: событие ждёт, пока потребитель по одному разберёт всё неистёкшее перед ним. Поэтому задержка события ≈ TTL.
- Защита канала (§4) поставила `frame_meta` на паузу (очередь > 300) и не дала очереди дорасти до 2000.
- **Исправление** — одна строка в `RabbitSource`: `basic_qos(prefetch_count=200)` (или параметр `prefetch`). Ack по одному при этом можно оставить: при окне 200 они идут конвейером. С ним шлюз получит цифры §6.1.
- Владелец файла — Codex (CX-011), шлюз — A3. Тест `tests/test_transport_rabbit.py:378` ждёт `prefetch_count=1`, его нужно поправить вместе с кодом.
- Наблюдение A3 «edge на ноутбуке доставлял событие ~1.5 с и терял большую часть `frame_meta` по TTL» — того же происхождения, только с другой стороны. Публикатор ждёт подтверждения каждого сообщения, и через VPN это те же ~4 сообщения/с. На стенде RTT до брокера 1 мс, и потерь нет.

### 7.2. Прочее

- **Spinning потоков onnxruntime в хвостах linq-tpu.** Хвосты (DFL-декод, ~1 мс) создаются с 2 потоками и активным ожиданием. На стенде это 91 мс CPU на вызов вместо 21.6 мс (замер 09:44). Три хвоста съедали квоту контейнера: до исправления было 0.9–2.8 к/с на камеру при CPU 100 % (уже на субпотоке 360p), после — 4.8–5.0 к/с при 65–72 %.
  - Edge отключает spinning для всех сессий ORT процесса (`guard/edge.py::disable_ort_spinning`, отключается `GUARD_ORT_SPINNING=1`).
  - Правильное место для исправления — `guard/inference/linq_tpu.py::load`: `intra_op_num_threads = 1` и `session.intra_op.allow_spinning = 0`. Владелец — A1/Codex: этот файл менялся в CX-018, поэтому A10 его не трогал.
- **Часы стенда отстают от NTP на 3.66 с.** Метки времени edge (`started_at`, `confirmed_at`, `ts`) идут по часам стенда. Сравнивать их с часами ноутбука напрямую нельзя: «возраст» события выйдет на 3.3 с больше реального. Gateway A3 оценивает сдвиг по `frame_meta` (`ts_offset`). Для точных задержек есть `metrics.edge.clock`.
- **CRUD камер в gateway не доходит до edge.** UI шлюза меняет только локальный `configs/cameras.yaml` ноутбука. Edge читает `configs/cameras.stand.yaml` на стенде при старте; канала конфигурации gateway → edge нет. Чтобы изменения заработали, их нужно перенести в `configs/cameras.stand.yaml`, затем выполнить `tools/stand.py sync` и `restart`.
