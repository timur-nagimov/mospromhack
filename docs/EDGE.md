Код edge — `guard/edge.py`, конфиги — `configs/cameras.stand.yaml` и `configs/models.stand.yaml`, замеры — `guard/edge_probe.py`, сырые цифры — `edge-*.json`.

Все замеры ниже сняты 24.10 на прежнем транспорте edge → шлюз: exchange `zazerkalye`, очередь `zazerkalye.gateway` (§1, §4). В main edge и шлюз переведены на протокол `guard.edge.v1` с SQLite outbox (`docs/EDGE_PROTOCOL.md`, пакеты `guard/edge/`, `guard/gateway/`, `guard/transport/`); на нём эти замеры не повторялись.

## 1. Схема

```
Jupyter-контейнер стенда (1.5 CPU, 4 ГиБ)                                  Ноутбук
 ┌────────────────────────────────────────────────────────────────────┐
 │ 4 × FileSource 640×360, 25 к/с → выборка 5 к/с                    │
 │   → letterbox → RawCodec (int8) ─► RabbitMQ tpu.direct ─► LinQ TPU │
 │   ◄─ выходы головы ─ хвост ONNX (DFL) → декод + NMS → ByteTrack    │
 │   → правила → EventManager → EdgeSink ─► exchange zazerkalye ──────┼──► очередь zazerkalye.gateway
 └────────────────────────────────────────────────────────────────────┘      (VPN-контейнер, 127.0.0.1:5672)
                                                                             → gateway: журнал, WS, UI
```

- Брокер для TPU и для нашего канала один и тот же — `10.0.114.30:5672`. Со стенда RTT 1 мс, с ноутбука через VPN — 225 мс.
- Модели: det и pose — YOLOv8n 480, ppe (YOLOv8s) и fire — 640. Все на TPU, программы O5, raw-режим (`docs/LINQ_NOTES.md` §13–16).
- Камеры `cam_s1`…`cam_s4` — те же, что в демо (`configs/cameras.yaml`): ролики s1_01 (зона), s2_01 (СИЗ), s3_02 (падение), s4_02 (техника). Зоны и правила совпадают, поэтому gateway показывает камеры по своему конфигу. Проверяет это `tests/test_edge_stand.py`.

## 3. Запуск, проверка, остановка

Демо одной командой — `scripts/run_tpu.sh`: VPN-контейнер → edge на стенде (если не запущен; `SYNC=1` — залить код и перезапустить) → очистка `zazerkalye.gateway` от накопленного без шлюза → шлюз с UI на `127.0.0.1:8000`. Остановка шлюза — Ctrl+C, edge на стенде — `python tools/stand.py stop`.

```bash
python tools/stand.py start          # ~/guard311/bin/python -m guard.edge --config configs/cameras.stand.yaml
python tools/stand.py status         # PID, RSS, CPU и хвост лога
python tools/stand.py logs -n 100    # раз в 10 с строка "stats: fps … | cpu ctr … | sent … | gw consumers …"
python tools/stand.py health         # hub, сервер, процесс, очередь
python tools/stand.py stop           # SIGTERM группе процессов; edge дожидается отправки и пишет сводку "edge stopped: {…}"
python tools/stand.py restart        # stop + start
```

- `start` запускается с `OMP_NUM_THREADS=2` и `GUARD_BACKEND=linq-tpu`. Остальное edge берёт из секции `edge:` файла камер: реестр `configs/models.stand.yaml`, `~/work/models`, `~/work/mosprom/data_360`, брокер стенда, raw, окно 4.
- Приоритет настроек: флаги CLI > переменные `GUARD_*` > секция `edge:` > значения по умолчанию.
- Поправка стенда под int8: у `zone_intrusion` на cam_s1 `min_conf` 0.45 вместо 0.5 в `configs/cameras.yaml`. Уверенность int8 на TPU в среднем на ~0.05 ниже, чем на CPU (docs/LINQ_NOTES.md §16). Остальные правила стенда совпадают с `cameras.yaml`; `tests/test_edge_stand.py` проверяет это явно (`STAND_INT8_OVERRIDES`).
- Прогон на CPU того же контейнера (для сравнения):
  ```bash
  python tools/stand.py restart --cmd "exec ~/guard311/bin/python -m guard.edge --config configs/cameras.stand.yaml --backend onnx-cpu"
  ```
- Проверка без брокера, лог вместо транспорта: `~/guard311/bin/python -m guard.edge --config configs/cameras.stand.yaml --transport log --duration 45`.

**Проверка с ноутбука** — замеряющий подписчик:

```bash
# шлюз работает (демо): копия потока через свою очередь, у шлюза ничего не отнимает
python -m guard.edge_probe --tap --duration 300 --out edge-tpu-$(date +%Y%m%d-%H%M).json
# шлюза нет: замер сам становится потребителем очереди шлюза (иначе edge не шлёт frame_meta и metrics, §4)
python -m guard.edge_probe --duration 300 --out edge-tpu-$(date +%Y%m%d-%H%M).json
```

- Подписчик читает `zazerkalye.gateway` через `127.0.0.1:5672` и печатает сводку (события, задержки, потери, часы).
- **Если шлюз работает, замер запускать только с `--tap`.** У общей очереди брокер раздаёт сообщения потребителям по очереди: шлюз недосчитывается половины `event`, создаёт событие из `event_update` уже без снапшота и с опозданием на 6–14 с (так было 24.10 12:34–12:44, когда замер стабильности шёл параллельно с демо). `--tap` читает копию потока через свою временную очередь на тех же ключах и шлюзу не мешает. Без `--tap` подписчик предупреждает о чужом потребителе (`consumers_before`).
- `--prefetch 1 --ack-every 1` воспроизводит поведение `RabbitSource` шлюза (§7.1).

## 4. Что публикует edge

| Сообщение | Когда | Содержимое | Размер |
|---|---|---|---|
| `event` | событие подтверждено | Event + снапшот JPEG (≤ 640 px, q≈70, ≤ 60 КБ). В `details.edge`: `node` и `sent_at` (epoch по часам стенда в момент передачи в транспорт) | ~25 КБ |
| `event_update` | событие закрыто или изменено | Event без снапшота | ~0.8 КБ |
| `frame_meta` | каждый обработанный кадр | `camera_id`, `frame_idx` (позиция в файле), `ts`, рамки людей и объектов с ID трека, нарушители. Флаги: бит 0 — нарушитель | ~150 Б |
| `metrics` | раз в 2 с | как `/api/metrics` + ключ `edge` (ниже) | ~6 КБ |
| `heartbeat` | раз в 2 с | `node_id`, `ts` | ~70 Б |

`metrics.edge`:
- `cpu` — `container_cores`, `container_pct_of_limit` (cgroup v2: `cpu.stat`, `cpu.max`), `process_cores`;
- `memory`;
- `clock` — сдвиг часов стенда по NTP, `offset_ms` и `uncertainty_ms`;
- `transport` — отправлено по видам и камерам, задержано защитой канала, вытеснено из очереди отправки, состояние очереди шлюза;
- `frames_processed` по камерам, `events_created`, `uptime_s`.

### Защита канала (`gateway_guard`)

Очередь `zazerkalye.gateway` одна на все виды сообщений. У событий и метрик нет TTL. TTL `frame_meta` (10 с) RabbitMQ применяет только к голове очереди, а событие в голове TTL не имеет. Без потребителя очередь за ~100 с дорастает до `x-max-length` = 2000, брокер начинает отклонять публикации (`reject-publish`), и канал встаёт. Когда gateway подключится, ему придётся разбирать тысячи устаревших сообщений.

Поэтому edge раз в 2 с смотрит очередь (passive declare по отдельному соединению):
- нет потребителя — не шлёт `frame_meta` и `metrics`, а `heartbeat` шлёт раз в 30 с;
- в очереди больше 300 сообщений — приостанавливает `frame_meta`, возобновляет ниже 150;
- события отправляются всегда.

В метриках это видно как `transport.held_by_guard` и `gateway_queue`. Отключение — `--no-gateway-guard` или `gateway_guard: {enabled: false}`.

## 5. Методика замеров

- **Подписчик:** `guard/edge_probe.py` на ноутбуке, `prefetch` 200 и групповой ack. При таком режиме потребитель не ограничивает канал (о `prefetch` 1 — §7.1).
- **Часы.** У стенда и ноутбука разные часы: стенд отстаёт от NTP на **3.66 с**, ноутбук — на 0.33 с. Разность D = часы ноутбука − часы стенда оценивается двумя способами:
  - по NTP: edge публикует свой сдвиг в `metrics.edge.clock` (pool.ntp.org, RTT 4 мс), подписчик меряет свой (RTT 222 мс);
  - по RTT: min(t_получения − ts heartbeat/metrics) − RTT_min/2 по 294 сообщениям, RTT_min ноутбук ↔ брокер = 224.6 мс.

  Результаты: 3335.1 и 3334.0 мс, расхождение **1.1 мс**. Формальная погрешность каждого способа — ±112 мс (RTT/2 ноутбука), но совпадение двух независимых оценок говорит о реальной точности в единицы миллисекунд.
- **Сквозная задержка оповещения** = t_получения на ноутбуке − D − `Event.started_at` (захват первого нарушающего кадра на стенде). Разложение:
  - окно подтверждения `confirmed_at − started_at`;
  - edge: от кадра подтверждения до передачи в транспорт, `sent_at − confirmed_at` (ожидание кадра в слоте, конвейер, снапшот);
  - канал `t_получения − D − sent_at`.
- События, ушедшие с edge до подключения подписчика (`sent_at` раньше начала приёма), из задержек исключены: они ждали в очереди. В отчёте это `backlog_excluded`.
- **Потери `frame_meta`** = 1 − полученные / прирост `frames_processed` за окно между первой и последней метрикой. Каждый обработанный кадр даёт один `frame_meta`.

## 7. Проблемы и ограничения

### 7.1. Шлюз брал сообщения по одному (`RabbitSource`, prefetch 1) — исправлено в da4c4cc (`CONSUMER_PREFETCH = 200`)

`guard/transport/rabbit.py::_connect` для потребителя вызывал `basic_qos(prefetch_count=1)` и подтверждал каждое сообщение отдельно. Брокер отдаёт следующее сообщение только после ack, поэтому через VPN (RTT 225 мс) потребитель брал не больше ~4 сообщений/с. Edge шлёт 20.7 сообщения/с. Замер `edge-tpu-prefetch1-20261024-1009.json` (150 с, `--prefetch 1 --ack-every 1`, тот же edge на TPU):

| | prefetch 200 (§6.1) | prefetch 1, как в шлюзе |
|---|---|---|
| принято сообщений/с | 20.7 | **3.5** |
| сквозная задержка оповещения p50 / p95, с | 2.20 / 2.53 | **12.64 / 12.92** |
| канал стенд → ноутбук p50, с | 0.15 | **10.45** |
| `frame_meta`: задержка p50, с / потери | 0.32 / 0.02 % | **10.24 / 93.5 %** |

- Голову очереди держат `frame_meta` с TTL 10 с: событие ждёт, пока потребитель по одному разберёт всё неистёкшее перед ним. Поэтому задержка события ≈ TTL.
- Защита канала (§4) поставила `frame_meta` на паузу (очередь > 300) и не дала очереди дорасти до 2000.
- **Исправление** в main: `CONSUMER_PREFETCH = 200` в `guard/transport/rabbit.py` (коммит `da4c4cc`, по этому замеру). Ack по одному оставлен: при окне 200 подтверждения идут конвейером.
- **Живая проверка настоящим шлюзом** (`GUARD_MODE=gateway`, uvicorn на ноутбуке, очередь стенда; опрос `/api/events` раз в 1 с, поэтому к задержке добавляется до 1 с):
  - **до правки** (100 с, 11:45): в журнал пришло 58 событий со снапшотами, `/health` — `edge connected, node stand-linq`. Но живые события появлялись через **26–53 с** (p50 34.8 с): перед ними в очереди был хвост, накопленный, пока шлюза не было, а prefetch 1 разбирает его по сообщению за RTT;
  - **после правки** (120 с, 11:50, `edge-gateway-a3-prefetch200-20261024-1150.json`): 130 событий в журнале, 2055 `frame_meta`, 0 ошибок. Первые 3 живых события — 16–26 с: хвост ~115 событий со снапшотами (~3 МБ) идёт по каналу 0.1–0.4 МБ/с около 7 с. Дальше — **1.8–3.3 с** от начала нарушения до записи в журнале шлюза (12 событий, p50 ~2.6 с).
- Хвост после долгого отсутствия шлюза — ожидаемое поведение at-least-once: события не теряются, но приходят пачкой. Перед демо накопленное очищает `scripts/run_tpu.sh` до запуска шлюза. **При работающем шлюзе очередь не очищать и замеры запускать только с `--tap`.**
- Наблюдение шлюза «edge на ноутбуке доставлял событие ~1.5 с и терял большую часть `frame_meta` по TTL» — того же происхождения, только с другой стороны. Публикатор ждёт подтверждения каждого сообщения, и через VPN это те же ~4 сообщения/с. На стенде RTT до брокера 1 мс, и потерь нет.

### 7.2. Прочее

- **Spinning потоков onnxruntime в хвостах linq-tpu.** Хвосты (DFL-декод, ~1 мс) создаются с 2 потоками и активным ожиданием. На стенде это 91 мс CPU на вызов вместо 21.6 мс (замер 09:44). Три хвоста съедали квоту контейнера: до исправления было 0.9–2.8 к/с на камеру при CPU 100 % (уже на субпотоке 360p), после — 4.8–5.0 к/с при 65–72 %.
  - Edge отключает spinning для всех сессий ORT процесса (`guard/edge/__init__.py::disable_ort_spinning`, отключается `GUARD_ORT_SPINNING=1`).
  - Правильное место для исправления — `guard/inference/linq_tpu.py::load`: `intra_op_num_threads = 1` и `session.intra_op.allow_spinning = 0`. Этот файл менялся в CX-018; правка в рамках данного замера не выполнялась.
- **Часы стенда отстают от NTP на 3.66 с и уплывают** (3640 мс в 09:50, 3756 мс в 11:12 — ~1.4 мс/мин). Метки времени edge (`started_at`, `confirmed_at`, `ts`) идут по часам стенда. Сравнивать их с часами ноутбука напрямую нельзя: «возраст» события выйдет на 3.3 с больше реального. Gateway оценивает сдвиг по `frame_meta` (`ts_offset`). Edge публикует NTP-сдвиг раз в минуту (`metrics.edge.clock`).
- **Обрыв VPN.** 24.10 ~10:21–11:00 туннель VPN-контейнера переподключался (tun0 сменил адрес). `tools/stand.py restart` висел ~40 мин, подписчик падал с `AMQPConnectorStackTimeout`. Edge на стенде при этом работал. Перед замерами и демо — `infra/vpn/vpnctl.sh status`.
- **CRUD камер в gateway не доходит до edge.** Прежний шлюз (транспорт `zazerkalye`) менял только локальный `configs/cameras.yaml` ноутбука. Шлюз в main правку камер отклоняет (HTTP 409, «Configure cameras on the edge»): каталог камер приходит с edge. Edge читает `configs/cameras.stand.yaml` на стенде при старте; канала конфигурации gateway → edge нет. Чтобы изменения заработали, их нужно перенести в `configs/cameras.stand.yaml`, затем выполнить `tools/stand.py sync` и `restart`. Зоны и правила обоих файлов сейчас совпадают (проверяет `tests/test_edge_stand.py`). Правка зоны в UI на демо будет видна в оверлее шлюза, но не в событиях edge.
- **События без шлюза копятся в очереди.** Защита канала держит телеметрию, но события идут всегда, и gateway получит их при подключении с опозданием. Для журнала это правильно: событие не теряется. В замере такие события исключены.
- **TPU-воркер общий для команд.** Ночью `inference_time` для det 480 был 8 мс, в 09:54 — 34 мс (p50), в 10:02 — снова 8 мс. От нагрузки других команд зависят `transfer` и `inference_time`.
- **Откаты на CPU из-за затыков воркера (CX-018).** С 12:06 воркер TPU время от времени не отвечал дольше 2 с: таймаут ответа по умолчанию в `linq_tpu.py` (`LINQ_TIMEOUT_S` = 2). За 53 минуты — 13 откатов на CPU, всего 203 с (6.3 % времени, `inference.switches` = 26, `fallback_seconds` = 203).
  - На каждый откат `FallbackBackend` 15 с работает на CPU, а 1.5 ядра контейнера 4 камеры не тянут: 0.3–1.8 к/с (§6.3).
  - Модели CPU грузятся при первом откате и остаются в памяти: RSS вырос с ~310 до ~580 МБ (не утечка, скачок в момент первого отката).
  - В замерах 10:02 и 11:33 откатов не было (`switches` = 0).
  - Брокер на стенде отвечает за 1 мс, поэтому 2 с тишины — это затор воркера, а не обрыв сети. С 12:32 на стенде `linq.timeout_s: 5` (секция `edge`). Результат — §6.4.
- **`tools/stand.py` (CX-015), исправлено:**
  - временные файлы загрузки были скрытыми (`.stand-upload-*`), а contents API Jupyter не создаёт скрытые файлы (`allow_hidden = False`, HTTP 400). Переименованы в `stand-upload-*`;
  - `state` теперь создаёт `~/work/mosprom`: на чистом сервере первый `sync` падал.
- **`configs/models.yaml`:** `tpu_program` для ppe (`ppe_640`) и fire (`fire_640s1`) включены в 10:06 (`1018c62`), сверка этих программ с CPU — `docs/LINQ_NOTES.md` §17. Реестр стенда (`configs/models.stand.yaml`) использует те же ppe_640 и fire_640s1.
- **FileSource декодирует все кадры** с родной частотой (25 к/с), даже если анализируется 5 к/с. Поэтому на edge используется субпоток 640×360 (§2). Ещё дешевле — `grab()` без `retrieve()` для кадров, которые не пойдут в анализ (изменение `guard/sources/video.py`).
- **Параметры правил** на стенде те же, что подобраны для демо (`configs/cameras.yaml`, 24.10 11:20). Исключение — `min_conf` у `zone_intrusion`: 0.45 вместо 0.5, потому что уверенность int8 на TPU ниже на ~0.05 (LINQ_NOTES §13). Подбор сделан на CPU и det 640; на TPU (det 480, порог 0.25) его стоит перепроверить офлайн-оценкой.
