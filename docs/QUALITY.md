## Методика

**Прогон.** `run_offline` читает ролик потоково, выбирает кадры с `sample_fps` = 5 (время кадра — `t0 + frame_idx / fps`)
и прогоняет их через те же компоненты, что `CameraWorker` в сервисе: детекторы из `configs/models.yaml` (onnx-cpu),
ByteTrack, атрибуты (`assign_attributes`), правила-плагины, `EventManager`. Реального времени и пропусков кадров из-за
скорости нет, поэтому результат воспроизводим и не зависит от машины.

**Событие** — подтверждённое оповещение `Event`: `started_at` — первый нарушающий кадр кандидата,
`confirmed_at` — момент оповещения (окно `min_duration_s` с долей нарушающих кадров не меньше `min_ratio`).
Переоткрытие того же события не считается новым оповещением.

**Сопоставление** (`ml/eval/events_eval.py`) — отдельно для каждой пары (ролик, тип):
- предсказания перебираются по времени подтверждения;
- предсказание совпадает с меткой, если интервалы `[started_at, confirmed_at]` и `[t_start, t_end]` пересекаются с допуском 2 с;
- первое совпадение со свободной достоверной меткой — **TP**; совпадение только с уже занятой достоверной меткой — **дубль**;
  совпадение только с `uncertain` — **игнор** (ни TP, ни FP); иначе — **FP**. Несовпавшая достоверная метка — **FN**;
- **задержка** = `confirmed_at − t_start` метки. Она бывает отрицательной из-за допуска;
- `uncertain` — спорные случаи разметки: короткий заход, перекрытие, нарушение только по жилету, пограничное расстояние.
  Они не наказывают и не поощряют.

Сопоставление идёт по типу и времени, а не по человеку. Событие «нет жилета» у человека без каски засчитывается как TP
метки «нет каски», если совпадает по времени. В базе так совпали 3 из 6 TP СИЗ на s2_02.

**Ложные тревоги в час** считаются двумя способами: по всем 535 с (во всех роликах размечены все нарушения включённых
правил) и только по «чистым» роликам (68.9 с; одна ложная тревога там — это 52 в час).

**Повтор на кэше детекций.** Для перебора параметров детекции всех четырёх моделей по тем же кадрам сохранены один раз
с порогом 0.05. Повтор фильтрует их по порогам реестра и прогоняет трекер, атрибуты, правила и
`EventManager` из нужной версии кода. Повтор совпал со всеми четырьмя официальными прогонами из таблицы выше
событие в событие (те же времена, треки и концы событий).
Один вариант считается за 2–5 с вместо 8 мин. Проверено около 900 вариантов, все с метриками —
в `eval-onnx-cpu-variants-20261024.json`. Кэш (3 МБ) и скрипты лежат вне git:
`~/Desktop/mosprom-heavy.noindex/a9_eval/` (`README.txt` там же).

**Стресс-тест против переобучения.** Правило включается на роликах, где таких нарушений нет и они не размечены.
Любое оповещение там — ложное.

Ложные тревоги дают в основном люди на полу и в кровати. Это честная база для дообучения и правок правила.

## Скорость

Apple M3 Pro, onnxruntime 1.31 CPU, 2 потока, кадры подряд без батча: **5.7–5.9 к/с** в среднем по набору
(2680 кадров анализа за 446–470 с; итоговый прогон — 6.0 к/с). Скорость зависит от числа моделей на камере:
3.4 к/с при det + pose + ppe (clean_*), 16 к/с при одной det (s1_02, s4_02). На кадр: det 58 мс, pose 62 мс,
ppe 163 мс (YOLOv8s), fire 55 мс. Камера с правилами на det + pose + ppe на 2 потоках CPU не успевает за штатной
выборкой 5 к/с. Для нескольких камер нужен TPU, батч или более лёгкая модель СИЗ.

## Ограничения

- **Маленький набор.** 23 достоверных события; одно событие — 4.3 п. п. полноты. 95 % интервал Уилсона для R = 17/23 —
  [0.54; 0.87], для P = 17/17 — [0.82; 1.0]. По типам — 1–7 событий: S6 и S7 по одному, S5 и S8 нет вовсе.
- **0 ложных тревог на 535 с** означает лишь, что частота, скорее всего, ниже ~20 в час («правило трёх»: 3 / 535 с).
  На «чистых» роликах (68.9 с) граница ещё грубее — ~157 в час. Для честной оценки FP/ч нужны часы «пустого» видео с объекта.
- **Подбор и оценка на одних данных.** Отложенной выборки нет. Чтобы снизить оптимизм: параметры общие для типа правила,
  выбраны середины плато, есть стресс-тесты на чужих роликах. Перенос на новые камеры всё равно не гарантирован.
- **Ролики не наши.** Это стоковые и датасетные ролики со склейками: s2_02, s3_02 и s4_02 смонтированы из нескольких
  сцен. Трекер и `EventManager` переносят треки и события через монтаж. Это даёт и FN (s2_02), и «удачные» TP.
- **Хрупкие TP.** s1_02 48–60 с засчитан событием, которое началось на присевшей женщине (38.8 с) и подтвердилось
  в 47.4 с, перед ID-свитчем на вошедшую в зону. Совпало благодаря допуску 2 с. Три TP СИЗ базы на s2_02 были событиями
  «нет жилета» у людей без касок.
- **Задержка** считается от `t_start` разметки. Для людей, которые в кадре с первой секунды (s2_02, s4_01, s6_01),
  это время от начала ролика, а не от появления нарушения.
- Разметка СИЗ — по каске. Жилет исключён из правила по умолчанию. Если на объекте жилет обязателен, его включают
  на зоне `ppe_required`, понимая риск FP на спецовках.

## Рекомендации

**Демонстрационная конфигурация (`configs/cameras.yaml`).** Демо-конфиг на 10:15 сверен с T3 на тех же роликах
(текущий main, повтор офлайн; в живом демо ролики идут по кругу в реальном темпе, цифры могут слегка отличаться):

| Камера | Сейчас в `cameras.yaml` | С параметрами T3 | Что поменять |
|---|---|---|---|
| cam_s3 (s3_02) | 4/6 падений, задержка p50 3.3 с | **5/6**, p50 **2.4 с** | `immobile_window_s: 1.5`, `min_ratio: 0.5` |
| cam_s4 (s4_02) | 1/3, оповещение в 11.6 с | 1/3, оповещение в **6.6 с** | `min_vehicle_speed_bh: 0.05` |
| cam_s2 (s2_01) | 2/2, p50 5.2 с | 2/2, p50 4.9 с | `min_duration_s: 1.5` |
| cam_s1 (s1_01) | 2/2, 2.0 с | 2/2, 2.0 с | можно `min_conf: 0.5` (на s1_02 убирает дубль) |

Значения T3 одинаковы для всех камер, как в `scenarios.yaml`:
- `ppe_missing`: `params.required: [helmet]`, `min_duration_s: 1.5`;
- `zone_intrusion`: `params.min_conf: 0.5`;
- `fall_immobile`: `min_duration_s: 1.0`, `min_ratio: 0.5`, `params: {min_lying_s: 1.0, immobile_window_s: 1.5}`, остальное штатно;
- `vehicle_proximity`: `params.min_vehicle_speed_bh: 0.05`;
- для показа падений — s3_02 (5/6, задержка 2.1–4.2 с) и s3_01 (CX-019, 2.4 с).

**Владельцам кода** (цифры — повтор на кэше, текущий main + T3):
1. `guard/tracking/attributes.py::_phone_near_person` — сравнивать с **ближайшей** уверенной точкой головы, а не со средним.
   Эффект: телефон 0/1 → 1/1 (s6_01, задержка 2.2 с), итог 18/23. Стресс: правило телефона на всех 13 роликах — 0 FP.
   Тот же эффект даёт радиус 1.0 × высота головы при среднем.
2. `vehicle_proximity`: скорость техники считается по низу рамки, а у крупной или обрезанной кадром техники он стоит на месте
   (s4_01: 0.00–0.10 при реальном движении). Лучше брать центр или край рамки и компенсировать движение камеры.
   Классы `excavator`, `wheel_loader`, `dump_truck` модели ppe (на s4_03 `excavator` 0.75–0.9 весь ролик) в трекер
   объектов не попадают: он берёт только det. Для погрузчика нужен детектор с классом forklift: потолок S4 сейчас 2/4.
3. СИЗ: p95 задержки 16 с упирается в модель ppe. Порог ниже 0.4 даёт FP на каске со спины. Нужна двухступенчатая схема
   (человек → кроп головы → классификатор каски) или голосование «каска не видна N кадров при видимой голове».
4. `EventManager` (CX-017): нарушение другого трека переоткрывает недавно закрытое событие при IoU ≥ 0.3 и паузе ≤ `reid_gap_s` (5 с).
   На склейке s2_02 это съедает реальное нарушение (пауза 3.8 с). Сброс состояния при смене сцены (резкое изменение кадра)
   уберёт такие склейки у трекера и событий. С `reid_gap_s` 3 с — +1 TP, но это подгонка, по умолчанию не предлагаю.
5. Падение (CX-019): при пропуске детекции поза мигает в `unknown`, `lying_since` сбрасывается, и `min_lying_s` отсчитывается
   заново. Держать `lying_since` при кратком `unknown` (≤ 0.5 с) — устойчивее, чем занижать `min_lying_s`.
6. Курение: модель fire/smoke не видит сигарету, а дым ловится вместе с пылью. Нужна отдельная модель.
