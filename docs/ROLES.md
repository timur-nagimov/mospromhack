# Роли и права доступа

Целевой контракт для бэкенда и интерфейса. Планируемый источник матрицы прав — `guard/auth/roles.py`.
Разделы «Как устроено» дописывают исполнители.

Текущий статус: локальный выбор роли и меню реализованы в `frontend/src/domain/roles.ts`.
Справочник сотрудников и права новых API описаны в [EMPLOYEES.md](EMPLOYEES.md).
Вход, сессии и `guard/auth/roles.py`, описанные ниже, пока остаются планом реализации.

## Принципы

- **Минимум прав.** Каждый видит то, что нужно для его работы. Видео и снимки с людьми — только тем, кто отвечает за реакцию на нарушение
  (152-ФЗ: изображение человека — персональные данные).
- **Разделение обязанностей.** Что считать нарушением (зоны, правила) решает инженер по охране труда. Подключение камер, учётные записи
  и выкатку моделей ведёт администратор.
- **Проверка на сервере.** Интерфейс только прячет недоступное, решает всегда API: любой запрос без права получает 403.
- **Журнал действий.** Вход, изменение камер, зон, правил, статусов событий и учётных записей пишется в журнал: кто, когда, что, с какого адреса.

## Роли

| id | Название в интерфейсе | Кто это на производстве | Что делает в системе |
|---|---|---|---|
| `worker` | Сотрудник | рабочий, бригадир | Смотрит дашборды: сводку нарушений по участку, типам и сменам. Видит журнал событий без снимков и видео |
| `operator` | Диспетчер смены | мастер смены, диспетчер | Следит за камерами вживую, разбирает события: подтверждает, отмечает ложные, закрывает, пишет заметки. Выгружает отчёты |
| `safety` | Инженер по ОТ | специалист по охране труда и промбезопасности | Всё, что диспетчер, плюс настраивает опасные зоны и правила камер, проверяет кадры маховика данных, читает журнал действий |
| `admin` | Администратор | ИТ, владелец системы | Всё, плюс подключает и удаляет камеры (RTSP и др.), управляет учётными записями, запускает обучение и выкатку моделей |

Для назначения виновников действует отдельное правило: запись доступна только
`operator` и `admin`, инженер по ОТ читает сохранённый список.

Без входа доступны только `GET /health`, `GET /api/auth/config`, `POST /api/auth/login` и статика интерфейса (страница входа).

## API

| Метод и путь | Право | Что делает |
|---|---|---|
| `GET /api/auth/config` | — | `{auth_enabled, demo_login, demo_users: [{username, display_name, role}]}`. `demo_users` непустой только при `demo_login` |
| `POST /api/auth/login` | — | Тело `{username, password}`. Ставит cookie `guard_session` (HttpOnly, SameSite=Lax, Path=/), отвечает как `me`. Ошибка — 401 без уточнения, что неверно |
| `POST /api/auth/logout` | вход | Удаляет сессию и cookie |
| `GET /api/auth/me` | вход | `{username, display_name, role, role_title, permissions: [..]}`; без сессии — 401 |
| `GET /api/auth/roles` | вход | Роли с названиями, описаниями и правами (для страницы «Пользователи» и матрицы ролей) |
| `GET /api/users` | `users.manage` | Список: `username, display_name, role, active, created_at, last_login_at` |
| `POST /api/users` | `users.manage` | `{username, display_name, role, password}` → 201 |
| `PATCH /api/users/{username}` | `users.manage` | Любое из `display_name, role, password, active`. Последнего активного администратора нельзя понизить или отключить (409). Отключение и смена пароля закрывают сессии пользователя |
| `GET /api/audit` | `audit.view` | `?limit&offset&username&action&from&to` → `{items: [{ts, username, role, action, target, details, ip}], total}` |
| `POST /api/cameras/probe` | `cameras.manage` | Проверка потока до добавления камеры: `{source: SourceConfig, timeout_s?}` → `{ok, width, height, fps, codec, first_frame_ms, error}` и кадр-превью (base64 JPEG) |

Ответы: без сессии — 401 `{detail: "auth required"}`, без права — 403 `{detail: "forbidden", permission: "<право>"}`.

Действия в журнале: `auth.login`, `auth.login_failed`, `auth.logout`, `camera.create`, `camera.update`, `camera.delete`, `camera.probe`
(проверка потока: адрес без пароля и итог), `zones.update`, `rules.update`, `event.update`, `event.assign` (виновники инцидента),
`employee.create`, `user.create`, `user.update`, `flywheel.review`, `flywheel.capture` (кадр камеры в выборку), `flywheel.job`.

## Хранение и сессии

- Отдельная SQLite `GUARD_AUTH_DB` (по умолчанию `<data_dir>/auth.db`): таблицы `users`, `sessions`, `audit_log`.
- Пароли — `hashlib.scrypt` с солью на пользователя, сравнение за постоянное время. Пароли и хэши не попадают в логи и ответы API.
- Сессия — случайный токен 32 байта, в базе хранится его SHA-256. Срок — 12 часов (смена) со сдвигом при активности.
  Повторный вход в том же браузере закрывает прежнюю сессию. Смена роли, пароля, отключение и выход обрывают и открытые
  MJPEG и WebSocket (проверка раз в минуту).
- CORS с `allow_credentials` только для явного списка источников, без `*`.
- Изменяющие запросы (POST, PUT, PATCH, DELETE) и WebSocket с чужим заголовком `Origin` получают 403
  `{detail: "cross-origin request blocked"}` (WebSocket — код 4403): свой адрес (`Host`, `X-Forwarded-Host`), источники
  из `GUARD_CORS_ORIGINS` и локальные dev-серверы при запросе на локальный адрес проходят (`guard/auth/origin.py`).
- Подбор пароля: 10 неудач на пару «логин, адрес» или 30 неудач с одного адреса по всем логинам — 429 на минуту; неудачи, за которыми 15 минут не было новых, забываются.
- Адрес камеры с паролем или токеном (`rtsp://user:pass@…`, `?token=`) роль без `cameras.manage` получает замаскированным
  (`***`); PUT с замаскированным адресом его не меняет.

## Настройки

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `GUARD_AUTH` | `1` | `0` — вход выключен, все запросы идут как `admin` (тесты и старые скрипты) |
| `GUARD_DEMO_LOGIN` | `1` | Кнопки «Войти как …» на странице входа и смена роли в меню пользователя — для показа экспертам |
| `GUARD_AUTH_DB` | `<data_dir>/auth.db` | База пользователей, сессий и журнала действий |

При пустой базе и `GUARD_DEMO_LOGIN=1` создаются демо-учётки, пароль равен логину: `admin`, `safety`, `operator`, `worker`.
В README предупреждение: для реального объекта демо-вход выключить и пароли сменить.

При `GUARD_DEMO_LOGIN=0` демо-учёток нет: в пустую базу создаётся только `admin` со случайным паролем, пароль — в файле
`auth-initial-admin.txt` рядом с базой (права 600, в лог пишется только путь). Демо-учётки из старой базы, у которых пароль
ещё равен логину, при `GUARD_DEMO_LOGIN=0` не входят, их сессии не действуют: смените пароль
(`python -m guard.auth set-password <логин>`).

## Интерфейс

- Страница входа `/login`. При `demo_login` — кнопки ролей «Войти как …».
- Меню пользователя в шапке: имя, роль, «Выйти». При `demo_login` — «Сменить роль».
- Пункты меню и кнопки без права скрыты. Прямой переход на закрытую страницу — экран «Нет доступа» с названием нужного права.
- Стартовая страница — первая доступная: Мониторинг (`video.view`), иначе Аналитика.
- Новые страницы: «Пользователи» (`users.manage`) с матрицей ролей и прав; «Журнал действий» (`audit.view`).
- 401 от любого запроса — переход на вход. 403 — уведомление «Недостаточно прав: …».

## Безопасность: что проверено

Проверка глазами атакующего, 25.10; каждая попытка воспроизведена в `tests/test_security_review.py`.

| Проверка | Итог |
|---|---|
| Каждый маршрут `/api/*` и `WS /ws/events` без сессии и без права; `HEAD`, `OPTIONS`; слэш на конце, `%2F`, `..`, регистр, `//` | Обхода нет: права висят на маршруте, а не на префиксе пути. `HEAD` и `OPTIONS` — 405 без тела, слэш — редирект без данных |
| MJPEG, кадр, снимок и клип события ролью `worker` | 403 |
| Фиксация сессии (подсунутый токен), повтор токена после выхода, отключения, смены пароля; срок 12 ч | Подсунутый токен не принимается, повтор — 401. Исправлено: повторный вход закрывает прежнюю сессию браузера; смена роли обрывает открытые MJPEG и WebSocket |
| CORS с credentials | Только явный список, с `*` credentials выключены |
| CSRF: `text/plain`, `form-urlencoded`, `multipart` с cookie | JSON-маршруты отвечают 422. Исправлено: изменяющие запросы и WebSocket с чужим `Origin` — 403 / 4403; SameSite=Lax не спасал от страницы на другом порту и при `GUARD_AUTH=0` |
| Подбор пароля | 429 после 10 неудач на пару «логин, адрес». Исправлено: ещё 30 неудач с адреса по всем логинам — 429 (перебор логинов не раздувает журнал); одновременно не больше 4 проверок scrypt; неудачи старше 15 минут без новых забываются |
| Хэши, соли, токены и пароли в ответах, журнале действий и логах | Не найдены. Исправлено: пароль и токен в адресе камеры роли без `cameras.manage` видны как `***`; `?token=` маскируется и в журнале |
| `GUARD_DEMO_LOGIN=0` | Было: пустая база всё равно получала `admin/admin`. Исправлено: только `admin` со случайным паролем в файле; старые демо-учётки с паролем по умолчанию не входят |
| `X-Guard-Role` при включённом входе | Права не поднимает: роль берётся из сессии |
| `POST /api/cameras/probe` и адрес камеры (SSRF) | Исправлено: `rtsp` — только сетевые схемы, без `file://`, `concat:`, путей, link-local 169.254.0.0/16 (метаданные облака) в любой записи адреса; `webcam` — только номер устройства; `file`, `images` — путь без схемы, не в `/dev`, `/proc`, `/sys`. Проверка потока отвечает `ok: false, error_code: "bad_uri"` и ничего не открывает, создание и изменение камеры — 422. RTSP на 127.0.0.1 и в локальной сети разрешён |
| Журнал действий | Исправлено: добавлены `camera.probe`, `event.assign`, `employee.create`, `flywheel.capture`; смена пароля через консоль пишется как `user.update` от `cli` |
| Большое тело запроса без сессии | Исправлено: больше 8 МБ — 413 (FastAPI читает тело до проверки входа) |
| Ссылка события на файл | Исправлено: снимок и клип отдаются только с расширением кадра или ролика — `auth.db` и `guard.db` рядом не отдать |

Не исправлено, принято для показа:

- `Host` не проверяется: страница с DNS rebinding может обратиться к серверу на `localhost`. С входом ей нужен пароль,
  но демо-пароли публичны при `GUARD_DEMO_LOGIN=1`. Для объекта: `GUARD_DEMO_LOGIN=0`, сервер за прокси с HTTPS.
- Локальные страницы (`localhost` на другом порту) проходят проверку `Origin`, если запрос пришёл на локальный адрес:
  так работают dev-серверы интерфейса.
- `X-Forwarded-For` от 127.0.0.1 uvicorn принимает на веру: клиент на том же компьютере может менять адрес в журнале
  и обходить счётчик на адрес.
- Нет абсолютного срока сессии: при активности она продлевается без конца.
- `GET /health` открыт и показывает текст последней ошибки инференса.
- Имя хоста, которое указывает на адрес метаданных облака, проверка адреса камеры не ловит: DNS заранее не разрешается.
- Интерфейс с dev-сервера на адресе локальной сети (`http://192.168.x.y:5173` с прокси Vite) получит 403 на вход и изменения:
  добавьте источник в `GUARD_CORS_ORIGINS`; сервер пишет такую подсказку в лог один раз на источник.
- Счётчики подбора живут в памяти процесса и обнуляются при перезапуске; первый запуск с пустой базой и
  `GUARD_DEMO_LOGIN=0` — одним процессом (с `--workers N` файл первого пароля может не совпасть с базой).
