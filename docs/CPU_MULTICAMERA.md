# Проверка трёх камер на CPU

`tools/cpu_multicamera.py` — ограниченный по времени acceptance helper для настоящих `FileSource`, `CameraWorker`, ONNX Runtime, трекера, правил, SQLite и FastAPI HTTP/WS. Он использует три локальных оригинала без зацикливания, проигрывает их в реальном времени и не скачивает файлы. Запуск не требует TPU, RabbitMQ или сетевого сервера.

Из корня проекта с установленными зависимостями:

```bash
.venv/bin/python -m tools.cpu_multicamera --json --timeout 120
```

В worktree можно использовать Python основного checkout и явно передать общие входы:

```bash
/path/to/checkout/.venv/bin/python -m tools.cpu_multicamera \
  --data-dir /path/to/checkout/data \
  --models-dir /path/to/checkout/models \
  --output-dir /path/to/new-evidence-directory \
  --timeout 120 --json
```

Каталог `--output-dir` должен отсутствовать: старые результаты, база и медиа никогда не переиспользуются. Без этого аргумента создаётся уникальный каталог `data/cpu_multicamera/<UTC>-<id>/`. По умолчанию `data/` и `models/` берутся из текущего checkout; для стандартной структуры `.worktrees/<name>` — из общего checkout. `.env` и `Settings.from_env()` не используются. Настройки заданы явно: `mode=local`, `autostart=false`, `onnx-cpu`, ORT 2 потока, OpenCV 2 потока, sampling 5 fps на камеру, без batching. Наблюдатель и WS подписываются до ручного `engine.start()`.

Нужны непустые локальные файлы:

| Камера | Путь относительно `data/videos/` | Зона |
| --- | --- | --- |
| `cpu_worker_zone` | `a3dev_worker_zone_detection/worker-zone-detection.mp4` | S1 `s1_01.mp4`, `behind_tape` из `tools/data_manifest.json` |
| `cpu_store_aisle` | `a3dev_store_aisle_detection/store-aisle-detection.mp4` | S1 `s1_02.mp4`, `aisle_far_right` из того же manifest |
| `cpu_people_load` | `a3dev_people_detection/people-detection.mp4` | Явный полигон полного кадра `full_frame_load_test`, только нагрузка |

Единственная модель — `models/yolov8n-640.onnx`, det YOLOv8, вход 640×640 float32. Первые две зоны копируются из manifest; третья не является разметкой качества. Используются полные оригиналы, примерно 76/65/50 секунд, а не 60-секундные фрагменты manifest. Фактические native frame count, fps и длительность записываются из метаданных каждого файла. Отсутствующие входы, неверный timeout и существующий output отвергаются до импорта inference/источников/FastAPI. `--help` также не загружает runtime.

Проверка считается успешной, когда выполнены все условия:

- На каждой из трёх камер реально активны `det` и правило зоны, есть обработанные кадры, нет ошибок worker/source/model/media и fallback-компонентов.
- Все три источника достигли EOF, их потоки завершились, `last analysis seq == last source seq`. Завершены все созданные клипы и их пути уже видны в HTTP-журнале. Один `media.pending=0` недостаточен: очередь не включает внутренний список ожидающих клипов.
- Получено событие `zone_intrusion` именно от `cpu_worker_zone`; неизменяемые поля совпадают между WS и HTTP. События от остальных камер не обязательны.
- JPEG HTTP каждой из трёх камер декодируется OpenCV.
- После штатного `engine.stop()` все события повторно читаются непосредственно из SQLite, совпадают идентификаторы и проверяемые поля, включая пути клипов. Потоки worker/source/media завершились, registry камер пуст, модель выгружена из backend.
- Для каждой камеры число кадров анализа составляет не менее **80% от `ceil(native_duration_s × 5)`**. Это выбранный порог acceptance, а не обещание производительности продукта. Пока источник работает, source и analysis должны продвигаться с паузами не более 5 секунд. Старый последний кадр после EOF не считается ошибкой freshness.

`/health` сохраняется для диагностики. Его `status=ok` не является критерием readiness.

В каталоге evidence сохраняются:

- `report.json`: итог, проверки, настройки, SHA-256 входов, версии пакетов, знаменатели и полные метрики каждой камеры.
- `frames-<camera_id>.jsonl`: каждое наблюдение исходного `CameraWorker.process`: `capture_id`, `seq`, `capture_ts`, `source_pos_s`, `done_wall`, `done_mono`, timings всех стадий, количества детекций и активные правила. Обёртка вызывает исходный метод ровно один раз, сохраняет его результат/исключение и восстанавливает метод при выходе. Реализации pipeline не заменяются.
- `cameras.json`, `models.json`, отдельные `guard.db`, `media/`, JPEG каждой камеры, WS-история и readback событий до/после stop.
- `runtime.log`: stdout/stderr изолированного runtime-процесса.

`per_camera.timings_ms` и `analysis_age_at_completion_ms` содержат `n`, p50, p95 и max за **весь** прогон, с линейной интерполяцией quantiles. Rolling-метрики API сохраняются отдельно как `metrics_rolling_diagnostic_only`; они не используются вместо полных percentiles. p95 камер не усредняется. `effective_processed_fps = frames_processed / native_duration_s`; coverage использует отдельный целевой знаменатель sampling. `source_frames - frames_processed` называется `skipped_by_sampling_or_overload`: разность включает сознательный sampling и не доказывает число потерь от перегрузки. `native_frames_not_published` отдельно отражает native-кадры, которые источник не опубликовал, в том числе при догоняющем `grab()`.

`three_camera_observed_overlap_s` — пересечение интервалов capture timestamp в наблюдениях трёх камер; ожидается около 50 секунд. RSS — high-water mark общего процесса, без приписывания памяти отдельной камере или модели. Этот helper проверяет завершённость и работу под нагрузкой; он не измеряет precision/recall, качество третьей зоны, RTSP, браузер или TPU.

Общий deadline по умолчанию 120 секунд, максимум 180. Runtime резервирует последние 10 секунд для shutdown. Родительский watchdog ограничивает весь дочерний процесс и при зависании посылает TERM, затем KILL только созданной им process group, включая её ffmpeg-потомков. На принудительное завершение отведено ещё до двух секунд. Зависание или незавершённые проверки дают `ok=false`; готовый JSON не превращает частичный прогон в успех. Код выхода: 0 — все проверки выполнены; 1 — preflight/runtime/timeout failure; 2 — неверный CLI или уже существующий output. При `--json` stdout содержит ровно один итоговый JSON, runtime-логи остаются в файле.

Узкие проверки helper, без запуска видео и модели:

```bash
.venv/bin/python -m pytest -q tests/test_cpu_multicamera.py
```

Финальная проверка после объединения SQLite persistence hooks и RabbitMQ topology fix повторена в `data/cpu_multicamera/20261024T020832Z-820289b0/`: **passed**, 76.86 с, 381/329/250 кадров анализа (960 всего), EOF и последний seq всех источников, 3 JPEG, 11 событий с SQLite readback после stop, успешное освобождение потоков/backend. Full-run total p95: 97.64 / 96.50 / 96.96 мс; наблюдённый общий интервал трёх камер 49.58 с. RSS high-water общего процесса — 721977344 байт. В первом прогоне ниже было 12 событий, во втором — 11; realtime sampling не задаёт фиксированную сетку кадров, эти числа не являются детерминированным quality benchmark. Обе записи сохранены; оценка качества использует отдельный последовательный runner.

Финальный API snapshot оставлен как rolling-диагностика: например, backend сообщает 960 вызовов `det`, но `infer.timings_ms.n=300` и p95 92.56 мс. Это ограниченное rolling-окно, не full-run n=960 и не полный percentile одной из камер. После EOF rolling fps камеры может стать нулевым, а `lag_s` — расти до остановки последней камеры; завершённый источник при этом не становится зависшим.
