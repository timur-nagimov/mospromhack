# Воспроизводимая оценка двух S1 видео на CPU

`python -m ml.eval.run_s1` — последовательная оценка реальных компонентов ORT → Detector → Tracker → S1 → EventManager → Journal. Она использует оба S1 из `tools/data_manifest.json`, первые 60 секунд исходных Intel worker-zone и store-aisle, модель `det` из текущего реестра. Сеть, async FileSource, engine/media, RTSP и TPU не запускаются. Асинхронный runtime проверяется отдельными smoke-инструментами.

Первый реальный CPU baseline обоих S1 выполнен 24.10.2026; его результаты и разбор ограничений приведены ниже. Результаты прежнего синхронного smoke на одном ролике не подменяют эту оценку.

## Команда

Из корня checkout в окружении с зависимостями проекта и подготовленными [моделью](MODELS.md) и [исходными видео](DATA.md):

```bash
python -m ml.eval.run_s1 \
  --data-dir /path/to/shared/data \
  --models-dir /path/to/shared/models \
  --timeout 180 --json
```

При отсутствии явных путей используются `Settings`, `GUARD_DATA_DIR`, `GUARD_MODELS_DIR`. Рецепт по умолчанию — `configs/eval-s1.json`; отдельный `--config` позволяет сохранить новую явно названную конфигурацию эксперимента. Пороговые параметры не меняются автоматически по результатам. Базовый scope требует оба ролика, 60 секунд, 5 FPS, два потока, `det` и `zone_intrusion`.

По умолчанию создаётся новый `data/s1_evaluation/<UTC-время>-<id>/`. `--output-dir` должен указывать на ещё не существующий каталог; прежние БД и результаты не перезаписываются. Общий wall timeout контролирует родительский процесс, включая зависший inference/декод. У рабочего процесса зарезервированы последние две секунды для завершения; принудительное прекращение process group может добавить до двух секунд. Все результаты находятся вне git.

Код выхода `0` означает полностью выполненную оценку и coverage; это не утверждение о достаточном F1. Даже ноль предсказаний даёт завершённую оценку с FN и нулевым recall. `1` — ошибка, timeout, неполный decode/coverage или ошибка компонента; `2` — неверный CLI или существующий выходной каталог. С `--json` stdout содержит один итоговый объект, runtime log сохраняется отдельно.

## Зафиксированные условия

`configs/eval-s1.json` хранит min_conf 0.35, min_box_h_px 40, min_duration 2 с, min_ratio 0.7, close_after 3 с, cooldown 30 с и tol 2 с. Значения Tracker совпадают с runtime Settings на момент создания baseline: high 0.4, low 0.1, new_track 0.45, IoU 0.25, buffer 3 с, min_hits 2. Тест отмечает будущий дрейф defaults; effective recipe и параметры модели сохраняются с каждым результатом. Полигоны берутся из самих S1 аннотаций manifest, основной конфиг камер не меняется.

Входные видео проверяются по SHA256, записанным в рецепте. Это исходные файлы Intel, не склеенные или перекодированные demo-копии. Сохраняются исходный manifest, config, effective камеры/ModelSpec, git HEAD и список изменённых tracked файлов, путь/mtime/размер/SHA256 runner, evaluator, конфигов, модели, metadata и обоих видео. В конце проверяется неизменность содержимого входов.

OpenCV использует два потока; реальный `OnnxCpuBackend` — intra-op 2 и inter-op 1, как в runtime. Torch и TPU SDK не импортируются. Загружается только `det`, проверяются отсутствие fallback, реальные классы с `person` и активное правило S1. Ошибки inference, правил и SQLite прерывают run; они не превращаются в пустые предсказания.

## Время, выборка и полнота

Для каждого видео создаются 300 целевых слотов `n / 5`, `n=0..299`. Выбирается первый исходный кадр на/после слота: `ceil(n × source_fps / 5)`. Это фиксированная сетка без накопления дрейфа от округлённого шага. `t=60` исключён. Время алгоритма — индекс исходного кадра / nominal FPS; границы ручных меток не округляются к слотам. Эта схема предполагает CFR исходников, а decoder `POS_MSEC` дополнительно сохраняется для аудита.

Последовательный reader проходит все исходные кадры `[0, 60)` и декодирует/обрабатывает все выбранные. Счётчики expected/traversed/selected/decoded/processed сохраняются отдельно. EOF до конца, пропущенный выбранный кадр или несоответствие счётчиков делают run неуспешным. Длительность 60 с попадает в `durations.json` только после завершения соответствующего ролика. Глобальная оценка создаётся после полного прохождения обоих — 600 / 600 выбранных кадров и 120 с exposure. Частичный результат не объявляется глобальной оценкой двух S1.

`mapping.json` связывает постоянный camera/capture ID каждого ролика с именем аннотации и `t0=0`: временные метки Event заданы в source-time. Синтетические timestamps не используются для live `lag_s`. `confirmed - label.t_start` — алгоритмическая задержка на временной шкале видео. Wall runtime и время ORT сохранены отдельно.

## Метрики и исключения

Matching выполняет существующий `ml/eval/events_eval.py` без изменения его семантики. Он жадно сопоставляет интервал `prediction.start..prediction.confirmed` с метками с допуском 2 с. Certain имеют приоритет над duplicate, затем uncertain. В обоих manifest S1 ровно **4 certain + 3 uncertain**. Uncertain не дают TP/FN, а совпавшие с ними предсказания исключаются только по правилам evaluator; все исходные метки и предсказания остаются в артефактах.

По каждому видео и глобально сохраняются исходные TP/FP/FN, duplicates, ignored_uncertain, precision/recall/F1, median/p95 algorithmic latency и false_alarms_per_hour. Поскольку исходный evaluator **исключает duplicates из precision и FP/hour**, рядом выводится явно отдельная строгая сводка:

```text
evaluator precision = TP / (TP + FP)
strict precision = TP / (TP + FP + duplicates)
evaluator FP/hour = FP / positive_video_exposure_hours
alarms_false_or_duplicate_per_hour = (FP + duplicates) / positive_video_exposure_hours
raw_predictions = TP + FP + duplicates + ignored_uncertain
recall = TP / (TP + FN)
```

Нулевые знаменатели precision дают 0, как в evaluator. Raw denominators, manual uncertain label IDs, prediction IDs с классификацией и причины исключения сохраняются отдельно. Классификация конкретных prediction ID получена prefix replay через тот же evaluator; второй matcher не реализуется.

Знаменатель FP/hour — **120 с двух положительных видео**, включая uncertain интервалы. Это не независимый clean-video benchmark и не false-positive rate на производственных чистых камерах. `clean_01/02` не добавляются в exposure: без независимых S1 полигонов они не дают содержательный отрицательный контроль этого правила. Uncertain исключения показаны явно; временной знаменатель evaluator из-за них не сокращается.

`lifecycle_*.jsonl` сохраняет новые, закрытые и переоткрытые ID. Cooldown может объединять разнесённые наблюдения; runner сохраняет такие переходы и итоговые открытые, цензурированные границей 60 с события, не меняя cooldown ради разметки. Предсказанием считается только фактическое новое подтверждение EventManager. При переоткрытии существующего ID дополнительное предсказание не синтезируется. `ended_at` отражается в Journal, но существующий evaluator не использует его при matching.

## Артефакты каждого run

- `report.json`: coverage, ошибки/статус, per-video/global original и strict метрики, provenance и ограничения;
- `predictions.json`: все созданные Event без фильтрации FP/duplicate/uncertain; `journal_events.json` — полный финальный readback и `guard.db`;
- `labels/*.json`, `labels_with_ids.json`, `mapping.json`, `durations.json`, `evaluation.json` в форматах существующего evaluator;
- `samples_*.jsonl`: target/source time, decoder position, source frame/capture ID, raw detections, tracks, нарушения, новые event IDs, timings;
- `lifecycle_*.jsonl`, effective config/model/camera, копия manifest, `runtime.log`, хеши результатов.

Выходы можно независимо переоценить тем же evaluator:

```bash
python -m ml.eval.events_eval --labels /path/to/run/labels \
  --preds /path/to/run/predictions.json --mapping /path/to/run/mapping.json \
  --durations /path/to/run/durations.json --tol-s 2 --out /path/to/recomputed-metrics.json
```

Наличие воспроизводимой оценки не означает промышленную готовность, измеренный многокамерный realtime, независимую валидацию полигонов или достижение заранее заданного качества.

## Почему s1_02 даёт FN 48–60 с

Подтверждено сохранёнными наблюдениями и кодом исполненного git HEAD:

1. Первый event `f3ab7904694e407d9ba22f0a7c793795` относится к track 5: start 27.4107, confirm 29.4127 с. Он сопоставлен с certain 26.8–47 с; последнее нарушение — 42.2088 с, уведомление о закрытии — 45.2118 с.
2. Второй event `4df304fdb7b849d69d1e4a8f582d254b` относится к track 3: start 38.2048, confirm 40.2068 с. Track 3 и track 5 одновременно присутствуют в trace, в том числе при втором подтверждении. EventManager действительно создал отдельный второй event; он не слил его с первым.
3. После второго подтверждения максимальный интервал между нарушениями track 3 — 2.002 с: 40.2068 → 42.2088. Это меньше `close_after_s=3`. У второго event нет ни закрытия, ни reopen: он непрерывно остаётся активным до конца выборки 59.8098 с. Следовательно, `cooldown_s=30` не является причиной этого объединения: стадия cooldown здесь вообще не наступила.
4. На участке 48–60 с track 3 наблюдается во всех **60 / 60** выбранных кадрах; S1 нарушение для него есть в **59 / 60**, новых event — **0**. Это не отсутствие выбранных кадров и не отсутствие frame-level S1 детекции. Тот же активный alias `(camera, rule, track_id)` вызывает `_touch`, а не новое подтверждение.
5. Evaluator сравнивает только интервал start..confirmed второго event: `[38.2048, 40.2068]`. Он пересекает уже занятую certain 26.8–47 с и uncertain 38–45 с. Приоритет certain/duplicate перед uncertain делает его **duplicate первого certain**, а не ignored uncertain. С допуском 2 с правая граница eligibility — 42.2068 с, что меньше начала второго certain 48 с. Позднейшая активность event и `ended_at=null` в matching не участвуют, поэтому certain 48–60 остаётся FN.

Это два разных уровня: на runtime уровне сохранилось одно активное нарушение track 3 через границу ручных эпизодов; на уровне оценки его единственное подтверждение относится к более раннему временному окну. Простая замена start..confirmed на весь срок жизни event изменила бы определение метрики и могла бы ошибочно засчитывать чрезмерно длинные события; она не является доказанным исправлением.

Не установлено: соответствует ли один и тот же track 3 одному физическому человеку до и после 48 с. Выходной ID 3 не меняется и не исчезает с 16.4164 до 59.8098 с, но это не доказывает отсутствие скрытого identity switch. В manifest нет actor ID, а описания uncertain 38–45 и certain 48–60 могут быть разными фазами одного участника либо разными участниками. По одним временным меткам и рамкам нельзя выбрать между этими объяснениями. Аналогично, temporal duplicate не доказывает, что второй человек является физическим дублем первого инцидента.

## Следующий конкретный issue и регрессия

Предлагаемый issue: **«S1: определить actor-aware связь непрерывного event через uncertain → certain и исключить temporal duplicate между разными участниками»**. Сначала нужна ручная привязка участников для двух одновременных событий s1_02 и согласованное определение: один непрерывный инцидент, переход от неопределённого наблюдения к certain или действительно новый инцидент. Затем можно версионировать ground truth/matching или исправлять подтверждённый tracking identity switch. Исходный baseline и его evaluator при этом должны сохраняться как отдельная версия. Уменьшать close_after/cooldown под границы разметки оснований нет.

Предлагаемые узкие regression fixtures без нейросетевого inference:

- Replay сохранённых нарушений track 3 с max gap 2.002 с и close_after 3: ровно одно подтверждение около 40.2068 с, никаких искусственных повторов на 48 с. Это защищает корректную непрерывность EventManager.
- Два одновременно наблюдаемых участника A/B с приведёнными label/event интервалами: текущая версия evaluator воспроизводит TP=1, FN=1, duplicate=1. Для будущей actor-aware версии предсказание B не должно становиться duplicate участника A; зачёт поздней certain B допустим только по явно принятой политике непрерывности, не через неявное изменение знаменателей.
- Отдельные отрицательные контрпримеры для будущей политики: один чрезмерно длинный event не закрывает два разных certain-инцидента; настоящий выход/повторный вход одного участника и реальная смена личности не подавляются как непрерывное присутствие. Expected значения задаются по actor-разметке, а не под желаемый F1.

В этом разборе изменена только документация: код, параметры, matcher и сохранённые артефакты baseline не менялись.
