# Движение против разрешённого направления (`wrong_way`)

Правило проверяет устойчивое движение точки опоры человека против явно заданной
стрелки внутри одной существующей зоны. Это положительное свидетельство движения
в плоскости изображения неподвижной камеры. Оно не измеряет расстояние в метрах,
скорость в м/с, намерение человека или допустимость маршрута вне настроенной зоны.
Камера, зона и стрелка требуют настройки под конкретный проход.

Плагин регистрируется автоматически через `@register_rule`, требует модель `det`
и имеет стандартную серьёзность `high`. По умолчанию он не добавляется ни в одну
камеру. Новых моделей, классов, зависимостей и вызовов inference нет.

## Опциональная конфигурация

```yaml
rules:
  - rule_id: corridor-wrong-way
    type: wrong_way
    zones: [corridor]  # ровно одна уже существующая зона камеры
    params:
      direction: [[0.2, 0.5], [0.8, 0.5]] # разрешено слева направо
      window_s: 2.0
      min_observed_s: 0.8
      max_gap_s: 0.5
      min_conf: 0.35
      min_box_h_px: 40
      min_displacement_bh: 0.25
      min_path_bh: 0.3
      max_angle_deg: 30
      min_progress_ratio: 0.8
    min_duration_s: 2.0
    min_ratio: 0.7
    close_after_s: 3.0
    cooldown_s: 30.0
```

`direction` обязательна: две разные конечные точки `[x, y]` с координатами
в `[0, 1]`. Вектор стрелки переводится в пиксели как `[dx * width, dy * height]`
и затем нормируется. Поэтому угол соответствует нарисованной стрелке и на
несимметричном кадре, например 1280×720. Стрелка задаёт разрешённое направление;
нарушением является движение против неё. Положение её начала не задаёт линию
пересечения. Проверка зоны использует низ-центр рамки человека и её расписание
`active_hours` в `Europe/Moscow`.

| Параметр | Смысл и ограничения |
| --- | --- |
| `window_s` | Максимальный возраст доказательств; конечное число в `(0, 10]` секунд. |
| `min_observed_s` | Минимальная длительность непрерывного наблюдаемого движения; положительная, не больше окна. Требуется минимум три точки. |
| `max_gap_s` | Максимальный промежуток между соседними наблюдениями; положительный, не больше окна. |
| `min_conf` | Минимальная confidence текущего трека, от 0 до 1. |
| `min_box_h_px` | Положительная минимальная высота рамки в пикселях исходного кадра. |
| `min_displacement_bh` | Положительное минимальное прямое смещение между начальной и текущей точками, делённое на среднюю высоту рамки. |
| `min_path_bh` | Положительная минимальная сумма длин шагов, делённая на ту же среднюю высоту рамки. |
| `max_angle_deg` | Максимальный угол каждого текущего шага и результирующего смещения к направлению против стрелки, `[0, 90)` градусов. |
| `min_progress_ratio` | Минимальное отношение результирующей проекции против стрелки к полной длине пути, `(0, 1]`. |

Неизвестные параметры, неконечные числа, логические значения вместо чисел,
неправильная стрелка, отсутствие/неоднозначность выбранной зоны, вырожденный
полигон и неправильное расписание отклоняются при создании плагина. JSON Schema
параметров доступна через существующий каталог типов правил.

## Наблюдаемость и временная семантика

Правило использует [общий контракт наблюдаемости](RULE_OBSERVATIONS.md).
В текущем контексте требуется `model_observations.det == observed`.
Отсутствующий статус, ошибка и неподдерживаемая модель очищают всю локальную
историю. Статус публикуется в `rule_observations[rule_id]`. Успешный пустой
результат модели считается наблюдаемым запуском, но не доказательством физической
безопасности.

В историю попадают только текущие `person`-треки с `last_seen == ctx.ts`, конечными
координатами, положительной рамкой, достаточными confidence/высотой и точкой опоры
в выбранной активной зоне. Используется время захвата кадра, а не время завершения
inference. История — собственные неизменяемые скалярные снимки; старая
`Track.history` не может задним числом дать доказательство.

Условия одного нарушающего кадра должны выполняться одновременно:

1. Не менее трёх наблюдений охватывают `min_observed_s` внутри `window_s`.
2. Каждый новый шаг продвигается против стрелки в пределах `max_angle_deg`.
3. Результирующее смещение и пройденный путь превышают свои пороги в высотах рамки.
4. Итоговая проекция против стрелки / путь достигает `min_progress_ratio`.

Остановка, шаг по стрелке или поперёк допустимого угла немедленно начинают новый
интервал с текущей точки. Поэтому старое окно не продолжает выдавать нарушение
после разворота. Даже небольшой противоречащий шаг сбрасывает доказательство:
это консервативное ограничение может снизить полноту на шумных траекториях.
Мелкое дрожание рамки и малый однонаправленный дрейф не достигают одновременно
минимальных смещения/пути; колебания также разрывают прогрессивный интервал.

Пропавший, устаревший, невалидный или низкоуверенный трек, выход из зоны,
неактивное расписание и разрыв больше `max_gap_s` удаляют его старые доказательства.
Повторное использование ID с новым `first_seen` начинает новую историю. Для
невалидного/устаревшего трека статус правила уточняется до `not_observable`;
при этом другой валидный человек всё ещё может дать положительное нарушение.

Повторный или обратный timestamp очищает все истории и не добавляет точку.
Неконечный timestamp или чужая камера возвращают `error`. Изменение размера
кадра также очищает все траектории. При новом capture production worker сначала
закрывает старые события с подтверждённым сохранением, затем пересоздаёт трекеры
и экземпляры правил; данное правило не переносит состояние между capture.

История ограничена 512 точками на трек и текущим окном. Состояние исчезнувших
людей удаляется на каждом вызове. Максимум — 256 одновременно представленных
людей; превышение лимита сбрасывает состояние и даёт `not_observable`, а не
произвольный выбор части толпы. Дубли ID внутри одного кадра дают `error`.

`EventManager` отдельно применяет `min_duration_s`, `min_ratio`, закрытие и
дедупликацию. `min_observed_s` — время построения траектории до первого
нарушающего кадра; оно не заменяет подтверждение события. Исчезновение
положительного сигнала останавливает его продление; событие закрывается по
обычному `close_after_s`, сохраняя последний нарушающий timestamp.

## Проверяемые доказательства и ограничения качества

`Violation.details` содержит нормированную стрелку и её единичный пиксельный
вектор, размер кадра, позиции/время/высоту рамки каждого использованного
наблюдения, длительность, среднюю высоту, результирующее смещение и проекцию,
длину пути, коэффициент прогресса, угол, единицы и фактические пороги. Эти данные
позволяют повторно вычислить решение. `Event` сохраняет снимок доказательства
подтверждения через существующий журнал; операторское решение не меняется
при последующем закрытии события.

Синтетические регрессии проверяют разрешённое/противоположное/поперечное движение,
остановку, дрожание, разворот, масштаб стрелки, наблюдаемость, разрывы времени,
исчезновение/повторное появление того же реального tracker ID, ограничение памяти
и путь реальный `Tracker → Rule → EventManager → Journal/outbox` без моделей.

Это не результат полевой валидации. Перед включением нужны отдельные видеосцены
с размеченным actor/зоной/разрешённым направлением/интервалом: разрешённое и
встречное движение, развороты, остановки, боковой выход, окклюзии, смена ID,
движение камеры и дрожание рамок. Нужны отрицательная экспозиция и разбор FP/FN
по сценариям, а не только успешный положительный пример. Перспектива и различия
в росте/размере рамок требуют настройки для камеры; отсутствие калибровки
не позволяет трактовать `bh` как физическое расстояние. Unit-тесты не
доказывают качество детектора, трекера или внешнего LinQ TPU.
