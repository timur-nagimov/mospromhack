# Расширение сценариев нарушений после выбора моделей

Статус: первый пакет реализован после решения сохранить текущую модельную конфигурацию. Добавлены `wrong_way`, `zone_dwell` и `zone_overcapacity`; их условия и ограничения описаны в [итогах пакета](VIOLATION_EXPANSION_RESULTS.md). Исходный аудит ниже относится к срезу `b131adedf7ed61261e6b4c5091237716df25a8b6` от 24.10.2026, ветка `feature/violation-expansion-plan`. Остальные сценарии остаются планом; действующие defaults, пороги и первичные benchmarks не заменяются.

Цель — больше полезных, различимых условий с проверяемым доказательством. Новое название существующей настройки не считается новым сценарием. Обнаруженный класс объекта сам по себе не доказывает нарушение: нужны область действия, связь с человеком/оборудованием и временное условие. Скорость исполнения описывается отдельно и не служит запретом на более качественную модель.

## Исходные десять правил на момент аудита

Реестр загружает плагины из `guard/rules/plugins`; API и форма параметров строятся по `type`, `required_models`, `params_schema`: [RulePlugin и registry](../guard/rules/base.py#L17). В текущем срезе есть ровно десять типов из [контрактов S1–S10](CONTRACTS.md#L54).

| Тип | Реальное условие и источник | Граница доказательства |
|---|---|---|
| `zone_intrusion` | Точка опоры человека внутри активного полигона; confidence и минимальная высота bbox — [evaluate](../guard/rules/plugins/zone_intrusion.py#L68) | Присутствие в настроенной зоне. Идентификация допуска/профессии человека отсутствует. |

| `fall_immobile` | Лежание и малое движение; bbox fallback и ограниченная эвристика потери трека после падения — [основной путь](../guard/rules/plugins/fall_immobile.py#L284), [lost-after-fall](../guard/rules/plugins/fall_immobile.py#L240) | Не доказывает потерю сознания. Владение и использование требуют более строгого доказательства. |
| `smoking_fire` | Классы `fire`, опционально `smoke`, confidence/площадь и зоны — [evaluate](../guard/rules/plugins/smoking_fire.py#L75) | Сигарету и действие курения не распознаёт. Заголовок плагина шире реализованного сигнала. |
| `fence_climb` | Геометрия ног/позы относительно fence, уменьшение высоты, низкое положение головы; fallback dwell — [evaluate](../guard/rules/plugins/fence_climb.py#L158) | Набор 2D эвристик. Fallback-пребывание нельзя выдавать за доказанное перелезание. |

Временное подтверждение, закрытие и дедупликация централизованы: [EventManager](../guard/events/manager.py#L483). По умолчанию `RuleConfig` задаёт окно 2 с и долю 0.7 — [контракт](../guard/contracts.py#L77). Это не универсальные параметры для каждого будущего сценария.

Плагины могут хранить ограниченную историю признака, но не дублировать механизм публикации событий. На смене capture worker сначала фиксирует закрытия, затем пересоздаёт правила и оба трекера: [capture boundary](../guard/pipeline/worker.py#L164). Новые состояния должны сбрасываться этим же путём; глобальные кэши по одному `track_id` не допускаются.

## Минимальные предпосылки

Это небольшие совместимые изменения перед новыми сценариями, а не новый rule framework. Изменения общих контрактов согласуются с зависимыми компонентами; независимые плагины используют общий интерфейс.

1. **Проверка capabilities выбранного профиля.** Сейчас [validate_camera](../guard/pipeline/engine.py#L259) проверяет наличие `model_id`, но не требуемых классов/атрибутов. Для каждого включённого условия нужны явные требования: person track, COCO-17 pose, конкретная пара положительного/отрицательного PPE-класса, vehicle class и т. п. Неподдерживаемая комбинация должна давать понятную ошибку/статус, а не формально включённое молчащее правило. Например, [registry](../configs/models.yaml#L135) прямо указывает, что respirator отсутствует; `no-mask` не заменяет его. Проверки одинаковы в API и offline doctor. Валидировать параметры нового плагина до сохранения камеры.

2. **Наблюдаемость отделена от результата условия.** В [worker](../guard/pipeline/worker.py#L245) inference error превращается в `[]`, а [FrameContext](../guard/contracts.py#L170) не передаёт состояние модели. Добавить минимальный статус входов `observed / not_observable / unsupported / error` с причиной и счётчики coverage по правилу. Успешная детекция без объектов не равна ошибке inference, но также не доказывает отсутствие человека в слепой зоне. Неизвестный интервал не добавляет подтверждающие наблюдения, не считается доказанно безопасным и не входит в отрицательную quality-экспозицию. Существующий `ended_at` остаётся концом наблюдаемого доказательства, а не утверждением об устранении опасности. Не менять исторические benchmarks задним числом.

3. **Явное подключение специализированной техники.** [Object tracker](../guard/pipeline/worker.py#L264) получает только `dets["det"]`. Machinery из PPE или будущий forklift detector автоматически в него не попадут. Нужна небольшая fusion-ступень: canonical classes, фильтрация нужных моделей, устранение двойных bbox до одного tracker, сохранение происхождения наблюдения. В текущих [PPE classes](../configs/models.yaml#L89) есть `excavator/wheel_loader/dump_truck`; список [OBJECT_CLASSES](../guard/pipeline/worker.py#L43) также требует согласования имён. Новый model_id должен входить в зависимости правила.

4. **Выбранная модель должна иметь runtime adapter.** RF quality tool ещё не production adapter. [Detector](../guard/pipeline/detector.py#L136) поддерживает YOLO, YOLO pose и D-FINE; для неподдержанного `raw` postprocess возвращает пустой результат. При выборе RF нужны отдельный корректный adapter и проверки source preprocessing, sparse classes, outputs. Нельзя объявлять подключение успешным по наличию ONNX. Прежний failed numeric parity RF сохраняется; качество, численная эквивалентность и TPU-готовность — отдельные gates.

Для всех новых геометрических правил проверять только реальные свежие наблюдения, finite координаты, монотонное время и максимальный допустимый разрыв. [Tracker](../guard/tracking/bytetrack.py#L373) сейчас возвращает подтверждённые активные треки; правило всё равно явно проверяет `last_seen == ctx.ts`, чтобы его доказательство не зависело от будущего изменения tracker/fallback. Статичная камера и валидная геометрия — явные условия применимости. Перемещение камеры/PTZ без обновления геометрии даёт `not_observable`, а не физическое движение объектов.

## Матрица расширения

P1 — новые условия поверх выбранного person detector. P2 — расширение после фиксации их контракта и данных. P3 — специализированные отношения, калибровка или внешние сигналы. Значения длительностей и порогов фиксируются по производственной политике и validation, до тестирования на frozen test.

| Приоритет / сценарии | Сигнал и временное условие | Калибровка, unknown и ограничения | Минимальная проверка данных и логики |
|---|---|---|---|
| **P1 — длительное пребывание в зоне** | Наблюдаемый человек непрерывно внутри дольше разрешённого dwell; короткое отдельное окно подтверждения | Разрешённый короткий заход отличает это условие от запрещённого входа. Полигон, расписание, max gap; потеря наблюдения прерывает доказанный dwell | Выход/возврат, пропуски, ID/capture change, разрешённое ожидание. Actor trajectories с входом/выходом |
| **P1 — движение против направления** | Устойчивое перемещение по истории против заданной стрелки | Статичная камера; угловой допуск и минимальный путь. Стояние/jitter — не нарушение. Не заявлять м/с | Правильное и поперечное направление, разворот, остановка, occlusion, монтаж |
| **P1 — превышение вместимости зоны** | Более N разных наблюдаемых людей в течение окна | N задаёт политика объекта. Видимое число — нижняя оценка; недобор не доказывает безопасность | N−1/N/N+1, двойные bbox, смена состава группы, две зоны, перекрытия |
| **P2 — запрещённое пересечение линии; вход/выход и счёт проходов** | Наблюдаемые позиции по разным сторонам ограниченного сегмента; hysteresis и ограниченный gap | Телепортация после reconnect не считается проходом. Подсчёт — аналитика; нарушение возникает только при запрете | Касание, ход вдоль линии, проход за её концом, повторные проходы того же человека, ID-switch; отдельная occurrence semantics |
| **P2 — одиночная работа / обязательный второй работник** | Один наблюдаемый человек плюс доказанная наблюдаемость всей рабочей зоны либо внешний сигнал присутствия | Отсутствие второй bbox недостаточно. Слепая зона/перекрытие → unknown. До доказательства coverage допустимо лишь сообщение «наблюдается один человек» | Скрытый напарник, вход второго, FOV loss, ошибка модели; при необходимости данные доступа/датчик присутствия |
| **P2 — техника на пешеходной полосе; запрещённая стоянка** | Vehicle track внутри зоны, движение либо неподвижность дольше лимита | Разметка полос, классы техники, разрешённые исключения. Camera motion выключает оценку скорости | Погрузчик/тележка/грузовик, обычный проезд, разрешённая остановка, изменение масштаба |
| **P2/P3 — сближение ближе X м; превышение скорости; задний ход рядом с человеком** | Ground-plane tracks, метрическая дистанция/скорость; для заднего хода ещё ориентация или сигнал машины | Homography/геометрия площадки с областью применимости и погрешностью. Разные уровни/обрезанные точки опоры → unknown. Пиксельный порог не заменяет безопасную дистанцию | Измеренные дистанции/скорости, перспектива, остановленная техника, разные уровни, occlusion |
| **P2 — падение, длительное лежание, устойчивый наклон/поднятые руки** | Видимые pose joints и временная история; переход падения отличать от статической позы | Длительное лежание сначала улучшает существующий S3, не считается новым типом без отдельного определения. Не заявлять диагноз/травму по позе | Сесть, лечь, наклониться, работать на коленях; низкий контраст и обрезанная поза; actor/episode GT |
| **P2 — очки, перчатки, защитная обувь, маска/респиратор, привязь** | Явные positive/negative классы, anatomical owner, видимая часть тела и temporal votes | Руки/стопы/лицо отдельно; перекрытие → unknown. Mask ≠ respirator; видимая привязь не доказывает анкерование, обычная обувь не доказывает защитный класс | GT present/absent/unobservable, парность рук/ног, owner ambiguity; объектные и событийные метрики отдельно по атрибуту |
| **P2 — использование телефона; курение** | Телефон/сигарета, однозначный владелец, связь рука–лицо и последовательность во времени | Вещь рядом с человеком не доказывает действие. Малый объект/закрытая рука → unknown. Телефон при движении уже параметр S6, не новый тип | Рация, инструмент, питьё, касание лица, телефон в кармане/у другого человека; видео действия, не только bbox |
| **P2 — открытый огонь / дым** | Специализированная модель, пространственная устойчивость и длительность | Зоны допустимого процесса; smoke не доказывает курение. Наблюдаемый класс и производственный запрет разделены | Сварка, пар, пыль, отражения, оранжевые объекты; длительные отрицательные видео |
| **P3 — перекрытый выход/проход; оставленный груз; пролив** | Устойчивое препятствие/сегментация в проходе; при необходимости связь груза с владельцем | Для свободной ширины нужна геометрия. Потеря владельца не доказывает оставление; блик не доказывает жидкость | Временный проход людей, разрешённое хранение, тени/блики, camera motion |
| **P3 — человек под подвешенным грузом; открытое ограждение работающей машины; нарушение допуска к горячим работам** | Специализированные object/relation/state модели плюс состояние оборудования/разрешения | Кадр обычно не определяет состояние машины, разрешение и 3D отношение. Неизвестное состояние блокирует категоричное нарушение | Синхронизированные labels машины/допуска, разрешённые операции, отсутствие геометрического пересечения в реальности |

Расписание доступа и разные обязательные СИЗ по зонам расширяют применение текущих правил через конфигурацию. Их не следует считать самостоятельными новыми алгоритмами. Дым/огонь и posture conditions сначала уточняют существующие сценарии, а не размножают равнозначные alarms.

## Первые три небольшие фичи

Общий prerequisite-коммит capabilities/observability интегрируется до параллельных веток. Для первого среза каждой фичи — одна явно выбранная зона на `RuleConfig`; разные зоны получают разные `rule_id`. Это сохраняет смысл текущего ключа события по камере/правилу/треку. Первые три фичи не требуют новых весов, новых ZoneKind или переписывания конвейера.

### `feature/rule-zone-dwell`

- Компонент: новый `guard/rules/plugins/zone_dwell.py`, `tests/test_rules_zone_dwell.py`, описание параметров/контракта.
- Условие: короткое пребывание разрешено, тревога после превышения заданного `max_dwell_s`. Отдельно задать max observation gap и допуск геометрической границы; не подменять dwell возрастом `first_seen` или общим confirmation window.
- Ограниченная память локального экземпляра по `(track_id, first_seen)`. Выход/потеря наблюдаемости прерывают доказанный непрерывный интервал; capture reset очищает его штатно.
- Acceptance: реальная цепочка Tracker → Rule → EventManager → Journal на синтетических траекториях; точные границы длительности, выход/возврат, ID-switch, повторный timestamp, две камеры, capture reset. Frozen размеченные видео показывают время фактического входа и допустимого/недопустимого dwell.

### `feature/rule-wrong-way`

- Компонент: новый `guard/rules/plugins/wrong_way.py`, `tests/test_rules_wrong_way.py`, описание направления в координатах изображения.
- Направление задаётся валидным ненулевым вектором/двумя нормированными точками. Проверять историю реальных наблюдений, минимальное перемещение и устойчивость направления; не переводить его в физическую скорость.
- Не выдавать решение при неподвижности, недостаточной истории, большом gap или невалидной геометрии камеры. Требования к движению камеры/обновлению конфигурации фиксируются явно.
- Acceptance: ход по/против/поперёк стрелки, разворот, jitter, остановка, occlusion, разные FPS, reset и отсутствие переноса истории между камерами. Video GT включает направление конкретного участника.

### `feature/rule-zone-overcapacity`

- Компонент: новый `guard/rules/plugins/zone_overcapacity.py`, `tests/test_rules_zone_overcapacity.py`, описание группового события.
- Условие: более N разных подтверждённых наблюдаемых людей в зоне в течение окна. Одно событие на зону: `track_id=None`, стабильная bbox зоны, details с `observed_count`, лимитом и IDs участников. Это нижняя оценка количества, без вывода «людей точно не больше N» при недетекции.
- Смена состава группы не должна создавать новые события. Временной confirmation/reopen остаётся у EventManager; плагин не публикует события сам.
- Acceptance: N−1/N/N+1, смена участников, дубли bbox/ID-switch, две зоны, временный провал наблюдаемости. Проверить закрытие/новый эпизод, Journal/outbox replay и сохранение операторского решения. Event details отражают доказательство на момент подтверждения; live occupancy считать отдельной телеметрией.

UI уже показывает заголовки новых типов через `/api/rules/types`: [fallback metadata](../frontend/src/domain/violations.ts#L171). Для первого среза достаточно schema параметров; специальный редактор стрелок/линий — отдельное улучшение. Не добавлять фиктивные defaults зон и не включать новые правила существующим камерам автоматически.

## Следующие фазы и модели

1. **Line-crossing и occurrence semantics.** Новый пакет после первых трёх правил. Одиночный crossing нельзя просто выдать одним `Violation` с общим `min_duration_s=2`: [confirmation](../guard/events/manager.py#L521). Повторный проход того же трека может быть объединён через cooldown/reopen: [matching](../guard/events/manager.py#L119). Зафиксировать pulse-подтверждение, re-arm после выхода из hysteresis и отдельные проходы в tests; только затем строить счётчик и запреты пересечения.
2. **Специализированная техника.** Закреплённый forklift/industrial-vehicle detector, canonical mapping и fusion до tracker. Сначала зоны/стоянка; метрические proximity/speed после калибровки. Наличие класса `truck` не доказывает надёжное обнаружение погрузчика.
3. **PPE по видимым частям тела.** Выбранная PPE-модель и ROI policy остаются baseline. Для новых атрибутов нужны negative classes с доказанной семантикой, anatomy/visibility и независимая оценка; только после этого расширять [attribute map](../guard/tracking/attributes.py#L13), [ROI attributes](../guard/pipeline/ppe.py#L14) и `ppe_missing.required`. Сохранить owner-bound ambiguity, одну запись vote на timestamp и current unknown без стирания истории — [shared helper](../guard/pipeline/ppe.py#L75).
4. **Pose/action.** Сильная person/pose семья с проверенной видимостью лежащего человека, COCO-17 mapping и source adapter. Для падения/курения/использования предмета при необходимости отдельный temporal model или relation head. Большая COCO-модель не создаёт отсутствующие PPE/action классы.
5. **Fire/smoke и cigarette.** Независимые датасеты и модели: модель огня не заменяет детектор сигареты с отношением к человеку. Новые fire negatives обязательно входят в evaluation, а representative positives — в отдельную TPU calibration.
6. **Сложные условия площадки.** Блокирование прохода, подвешенный груз, состояние ограждения/машины и разрешения реализуются по одному условию с собственными signal/data gates. Open-vocabulary модели из [каталога семейств](EXTENDED_MODEL_FAMILIES_20261024.md) могут помогать находить и предразмечать примеры; teacher output не становится GT без проверки человеком.

Каждая независимая фича — отдельная `feature/...` ветка и opt-in конфигурация. Семейство модели, поддерживаемые классы, input preprocessing и head format фиксируются до реализации правила. Не вводить крупный универсальный action framework заранее.

## Gates качества и целевого LinQ

**Семантика.** Для сценария заранее записаны условие, область действия, необходимые наблюдения, unknown reasons, единица эпизода и смысл ended_at. Detection, condition и подтверждённое Event различимы в трассе. Состояние модели/камеры не маскируется под безопасный кадр.

**Данные.** Frozen видео/изображения с SHA, sampling и точными capture boundaries. Разделение по камерам, людям и исходным видео, а не соседним кадрам. Нужны положительные эпизоды, целевые контрпримеры и длительная размеченная отрицательная экспозиция. Отдельно фиксировать training overlap и интервалы, где условие не наблюдаемо. Пустая аннотация для другого сценария не делает видео отрицательным для нового.

**Разметка взаимодействий.** Для людей/техники/PPE нужны actor/zone/pair IDs и необходимые условия, а не только совпадение времени. Текущий [LabelEvent](../ml/eval/events_eval.py#L62) и [evaluator grouping](../ml/eval/events_eval.py#L210) используют видео, тип и время. Расширенный протокол добавлять отдельно; старые scores не пересчитывать как будто actor GT существовал. Подтипы PPE не должны получать TP за другое нарушение того же человека в тот же момент.

**Метрики.** Отдельно: object/attribute AP и видимость; event precision/recall, duplicate alarms, latency, FP/час; unknown/error coverage. Не уменьшать denominator из-за неподдержанных классов. Для counting дополнительно ошибки числа/направления и пропущенные/дублированные проходы. Для метрической геометрии — ошибка в метрах/скорости и неопределённая область. Числовые пороги приемлемости определяются до held-out run, а не подбираются по его результату.

**Объём доказательства.** Unit и синтетические integration tests подтверждают логику, не качество модели. Текущие [13 demo-видео](DATA.md#L68) и короткая clean-экспозиция не подтверждают все будущие сценарии. Для S5/S8 документированы отсутствующие подходящие ролики: [DATA](DATA.md#L165). Исторический [QUALITY](QUALITY.md#L46) описывает около 900 вариантов на том же наборе; его итог не является независимой приёмкой текущего snapshot. Не интерпретировать ноль ложных тревог на коротком видео как промышленную надёжность.

**Реализация.** Profile/capability validation, наблюдаемость, reset на capture boundary, bounded память, partial persistence retry, replay/outbox и operator ownership не должны регрессировать. Как минимум один новый сценарий на пакет проходит целиком через production Worker → Journal → HTTP/WS с синтетическим backend; длительные видео оцениваются отдельно воспроизводимым offline runner.

**LinQ.** ONNX checker или успешный CPU benchmark не подтверждают компиляцию/качество TPU. Для выбранного кандидата закрепить export и source adapter, проверить допустимые operations/head split, shape/dtype/finite outputs, затем representative INT8 calibration отдельно от test. Проверить CPU/native/ONNX и реальный внешний TPU на одинаковых входах и event protocol; raw численные отклонения и quality delta описывать раздельно. Existing failed parity нельзя переименовать в pass по хорошему AP. Production route использует `linq-tpu` без скрытого CPU fallback — [контракт](CONTRACTS.md#L25). Совместимость современного семейства с компилятором считается непроверенной до фактической приёмки. Скорость и память остаются характеристиками, не veto качества.

## Что потребуется от площадки

Для активации правил нужны реальные зоны/направления, вместимость и допустимый dwell, обязательные СИЗ по операциям, допустимые процессы, предел ложных тревог и записи камер. Для метрической близости — калибровка и физические расстояния; для permit/machine-state условий — соответствующие внешние сигналы. Эти данные не блокируют подготовку кода и синтетических тестов, но ограничивают заявления о качестве и допустимые автоматические выводы.

Новые правила не включаются автоматически в рабочие камеры. Первый пакет реализован отдельными ветками после текущего выбора моделей; дополнительные модели и будущие сценарии требуют собственных измерений. Следующие крупные исследования я отложил до завершения интеграции.
