# Подготовка S2 и чистого контроля

Рецепты и временные метки берутся из `tools/data_manifest.json` без изменения
разметки, сегментов и порогов моделей. Для четырёх выходов нужны пять исходных
файлов. Их SHA256 и размеры перенесены из manifest ревизии `79a8920`;
локальная загрузка и кодирование в рамках этой правки не выполнялись.
Наличие pins ещё не подтверждает доступность файлов по сети или успешное
получение этих байтов в текущем окружении.

| Выход в `videos/` | Исходники и рецепт | Certain / uncertain | Метаданные до фактического кодирования |
|---|---|---:|---|
| `s2_01.mp4` | `intel_safety_gear`, от 0 до 60 с | 2 / 1 | План: 60 с, не более 1280×720, пропорции исходника |
| `s2_02.mp4` | Полные `mixkit_23237` + `mixkit_24049`, concat | 4 / 1 | По описанию manifest около 36.9 с; 1280×720 с полями |
| `clean_01.mp4` | Полный `mixkit_23107` | 0 / 0 | Длительность пока не измерена; не более 1280×720 |
| `clean_02.mp4` | Полный `mixkit_23224` | 0 / 0 | Длительность пока не измерена; не более 1280×720 |

Общие параметры: H.264/libx264, 25 FPS, CRF 28, preset `medium`, yuv420p,
без звука, faststart, 4 потока ffmpeg. Единственный сегмент сохраняет пропорции
и не увеличивается; стороны округляются до чётных. Многосегментный concat
вписывает каждый сегмент в 1280×720 с полями. Фактические длительность,
геометрия, число кадров, размер и SHA256 выходов до выполнения неизвестны.

Всего для S2 **6 certain + 2 uncertain** интервала `ppe_missing`.
В `s2_02` несколько людей размечены одинаковыми временными интервалами.
Actor GT/идентификаторов участников и покадровых person/PPE-рамок нет:
поле `persons` и текст `note` описательные. Эти метки сами по себе не позволяют
доказать соответствие треков физическим участникам или оценить actor-aware
recall. Uncertain остаются uncertain и не превращаются в дополнительные certain.

Оба `clean` — отрицательный контроль **только касок**: часть людей одета в
комбинезоны без сигнальных жилетов. Для PPE-контроля на них включают проверку
каски, проверку жилета отключают согласно `rules_note`. Это условие оценки,
а не автоматическая смена runtime-конфигурации загрузчиком. В `clean_02`
камера движется; статические зоны для него не заданы. Пустые `events` не
означают универсальный отрицательный контроль для любого правила.

## Идентичность исходников

| Source ID | Ожидаемые байты | SHA256 |
|---|---:|---|
| `intel_safety_gear` | 27 534 166 | `a0ba636766524dd0bdfa52a2a62108aafb585acd138cb0e08226d12ae35b64c5` |
| `mixkit_23237` | 6 721 285 | `e72baa23fb899ff9cfb5feeef01af167e68f3696af7b89b6fea2a28dabadcff2` |
| `mixkit_24049` | 5 261 599 | `36172448072224fef3db87b8ecf668e75a7613c2dcae13ec3298e97b47dbbb71` |
| `mixkit_23107` | 10 382 381 | `09bcf24f9dcc4156e6232a66db0262ba30c44ad32b13f35f07f3ce02aea449ac` |
| `mixkit_23224` | 10 761 089 | `d95a5150cd66389978c3f9353ad53f07f2f1f1b8bc6177f9ae863cf3d7eefef3` |

URL, страницы источников, авторы и лицензии сохранены в manifest. Intel URL
использует изменяемый `master`, Mixkit — CDN: сами URL не фиксируют содержимое.
Ожидаемые SHA256 и размер задают идентичность байтов; при изменении upstream
загрузчик откажет, а не примет новую версию под прежним именем.

`download` проверяет и новый файл, и существующий кеш `raw/<source>.mp4`.
Новый файл скачивается в отдельный временный файл в `raw/`, проверяется и лишь
затем атомарно публикуется. Ошибка SHA/размера завершает команду без повторного
скачивания; транспортные ошибки повторяются до трёх раз. Временный файл
удаляется при ошибке, существующий кеш не удаляется и не заменяется
непроверенными байтами. Повреждённый кеш не исправляется автоматически:
сначала сохраните его отдельно для диагностики, затем повторите загрузку.

Для старых источников manifest без SHA сохраняется совместимость: непустой
файл принимается, но это не доказательство byte identity. Если задан только
размер или только SHA, проверяется имеющийся pin. Пустой неприкреплённый кеш
можно скачать заново; новый пустой ответ не принимается.

## Команды подготовки

Из корня checkout в окружении проекта, с явно выбранным каталогом данных:

```bash
export GUARD_DATA_DIR="${GUARD_DATA_DIR:-$PWD/data}"
python tools/fetch_data.py --data-dir "$GUARD_DATA_DIR" \
  --only s2_01 s2_02 clean_01 clean_02 --steps download

python tools/fetch_data.py --data-dir "$GUARD_DATA_DIR" \
  --only s2_01 s2_02 clean_01 clean_02 --steps encode \
  --heavy "$PWD/tools/heavy.sh"

python tools/fetch_data.py --data-dir "$GUARD_DATA_DIR" \
  --only s2_01 s2_02 clean_01 clean_02 --steps labels
```

Загрузка дедуплицирует пять исходников. Encode выполняет ролики по одному
через указанную очередь тяжёлых задач; он повторно сверяет raw-входы даже
при отдельном `--steps encode`. `--force` по-прежнему означает только
перекодирование существующих выходов, а не повторное скачивание. Повреждённый
raw при `--force` блокирует ffmpeg и сохраняет прежний encoded output.
Существующий выход без `--force` пропускается; его наличие само по себе не
считается повторной верификацией качества или происхождения этого выхода.

Labels создаёт `labels/s2_01.json`, `labels/s2_02.json`, `labels/clean_01.json`,
`labels/clean_02.json` и обновляет `durations.json`, сохраняя остальные записи.
Если видео уже созданы, в labels записываются измеренные `duration_s` и `size`.
После подготовки нужно отдельно сверить четыре выходных файла и их
длительности/геометрию, записать размеры и SHA256; при необходимости получить
контрольные кадры отдельным шагом `--steps checks`. До такого readback
перечисленные рецепты не считаются выполненной подготовкой или quality benchmark.
