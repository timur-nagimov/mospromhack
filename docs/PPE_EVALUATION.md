# Оценка качества PPE-моделей

`ml/eval_ppe.py` сравнивает детекции моделей с разметкой YOLO. Он не обучает
модели и не меняет конфигурацию работающего конвейера.

```bash
python ml/eval_ppe.py --data /path/to/yolo-dataset --splits val test \
  --model person_only=/path/to/person.pt \
  --model ppe=/path/to/ppe.pt --device cpu --conf-op 0.35 --json ppe-eval.json
```

В наборе нужны `data.yaml` с `names`, изображения `images/<split>/...` и метки
`labels/<split>/...`. Ключ изображения — нормализованный путь относительно
`images/`, например `val/a.jpg` или `test/a.jpg`. Одинаковые имена в разных
сплитах и вложенных каталогах не объединяют разметку и предсказания.
Для сравнения моделей используйте один набор изображений, сплиты и настройки
инференса. Пропущенный файл меток сейчас означает отсутствие размеченных объектов
на изображении; перед оценкой проверьте полноту разметки.

## Метрики

Для каждого из классов `person`, `helmet`, `no_helmet`, `vest`, `no_vest`:

- `ap50` — AP при IoU ≥ 0.5. Предсказания сортируются по убыванию confidence;
  каждая GT-рамка сопоставляется не более одного раза. При равных confidence
  сохраняется порядок предсказаний.
- Precision превращается в невозрастающую огибающую. Для каждого recall из
  `0.00, 0.01, ..., 1.00` берётся precision в первой достигшей этого recall
  точке; недостигнутые точки дают ноль. AP — среднее этих 101 значений, как в
  [официальном COCO accumulator](https://github.com/cocodataset/cocoapi/blob/master/PythonAPI/pycocotools/cocoeval.py).
  Для 1 GT и 1 идеального TP AP равен 1; для 2 GT и 1 идеального TP — `51/101`.
- `p`, `r` — precision и recall только для предсказаний с confidence ≥ `--conf-op`.
  AP использует все возвращённые предсказания и не зависит от `--conf-op`.
- `n_gt` — число GT-объектов класса в выбранных сплитах.

Для `no_helmet@iou0.3` поле `ap` означает отдельную диагностическую AP при
IoU ≥ 0.3: границы головы/лица у разметки и модели могут различаться. Локальный
визуальный аудит выявил неоднородную геометрию и возможные пробелы исходного GT,
см. [MODEL_RESEARCH_20261024.md](MODEL_RESEARCH_20261024.md). Диагностику IoU 0.3
нельзя подменять AP50 при выборе по единой метрике.

Это AP50 с COCO-усреднением по recall, а не полный COCO mAP@[.50:.95].
Оценщик не реализует crowd/ignore и стратификацию по площади. Инференс использует
`conf=0.001`, NMS IoU `0.7`, `max_det=300` на изображение; это не официальный
COCO-протокол с `maxDets=100` на класс. Поле `ap_method` содержит
`coco_101_point`, `conf_op` сохраняет выбранную рабочую точку.

## Общий балл и покрытие классов

Совместимый ключ JSON `core_ap50(person,helmet,vest)` — среднее AP50 core-классов,
**имеющих GT в выбранном наборе**. Этот знаменатель общий для всех моделей:
класс, которого модель не поддерживает, при наличии GT даёт AP50, precision и
recall равные нулю. Например, при GT всех трёх классов идеальная person-only
модель получит `1/3`, а идеальная PPE-модель — `1`.

Если GT класса нет, его AP остаётся `null`: оценщик не придумывает качество
по отсутствующей разметке. Такой класс не входит в знаменатель. Для набора
только с `person` нельзя интерпретировать общий балл как качество по трём
PPE-классам. Если GT нет у всех core-классов, общий балл тоже `null`.
Среднее вычисляется до округления AP отдельных классов.

В `coverage` отдельно представлены:

- `model_supported_classes` и `model_unsupported_classes` — возможности модели
  по её словарю классов, а не по тому, встретились ли детекции;
- `classes_without_gt` — классы без объектов в выбранной разметке;
- `per_class` — `model_supported`, `n_gt` и `status`: `evaluated`, `unsupported`
  при наличии GT или `no_ground_truth` при его отсутствии;
- `core` — списки `classes_with_gt`, `classes_without_gt`, общий `denominator`,
  `supported_classes`, `unsupported_classes` среди классов с GT и
  `supported_fraction`. Консольная таблица выводит покрытие, например `1/3`.

Для обоснованного сравнения по трём core-классам нужен `denominator=3`.
В отличие от неподдерживаемого моделью класса, поддерживаемый класс с нулём
детекций получает `status=evaluated`, но его AP при наличии GT тоже равна нулю.

## Имена классов при экспорте и в runtime

Оценщик приводит, например, `Hardhat` → `helmet`, `NO-Hardhat` → `no_helmet`,
`Safety Vest` → `vest`, `NO-Safety Vest` → `no_vest`, `worker` → `person`.
Эта нормализация относится к оценке и автоматически в runtime не переносится.
Для экспорта модели с такими именами передайте явную карту:

```bash
python ml/export_onnx.py --weights /path/to/ppe.pt --imgsz 640 \
  --out ppe-640.onnx --model-id ppe \
  --class-map '{"Hardhat":"helmet","NO-Hardhat":"no_helmet","Safety Vest":"vest","NO-Safety Vest":"no_vest","worker":"person"}'
```

Ключи карты должны в точности совпадать с исходными именами в вашей модели.
Экспорт сохраняет канонические классы в metadata; проверьте поле `classes`
в `ppe.json`. Runtime ожидает канонические имена и роли `det`, `ppe`, `pose`,
`fire`. Сравнительное имя из `--model`, например `person_only`, не назначает
модели роль в конвейере.

Отсутствие детекции `helmet` или `vest` означает неизвестное состояние
(`None`), а не доказанное отсутствие СИЗ. Отрицательное наблюдение требует
явного класса `no_helmet` / `no_vest` и сопоставления с человеком. Высокая AP
положительных классов сама по себе не доказывает качество определения нарушений;
для этого нужна оценка событий и соответствующая разметка.
