- D-005 (24.10 01:05) **Конвейер распознавания работает на Jupyter-сервере стенда, рядом с TPU; ноутбук — шлюз UI.**
  - Почему (замеры A1, docs/LINQ_NOTES.md §9–10):
    - ноутбук ↔ стенд через VPN: RTT 235 мс, обратный канал 0.1–0.4 МБ/с;
    - YOLO 640 (вход 4.9 МБ, выход 2.8 МБ) с ноутбука — 4–10 с на кадр, это нежизнеспособно;
    - на Jupyter-сервере брокер отвечает за 1 мс: resnet50 даёт 7.8 к/с последовательно и 19 к/с при окне 4;
    - у сервера 64 ядра и 187 ГБ RAM, так что заодно разгружаем ноутбук после OOM.
  - Схема:
    - `edge`-процесс на сервере: источники (видео загружены на сервер) → препроцессинг → TPU через Rabbit (окно 4–8 задач) → постпроцессинг → трекинг → правила → EventManager;
    - edge публикует события (со снапшотом JPEG), компактные детекции по кадрам и метрики в наш канал;
    - ноутбук (FastAPI + UI) принимает их, ведёт журнал и показывает живое видео: те же видеофайлы проигрываются локально, а оверлеи рисуются по детекциям с сервера.
  - Канал сервер → ноутбук: своя очередь в Rabbit. Если свои очереди запрещены — HTTP через jupyter-server-proxy или выгрузка через Jupyter API. Проверяет A1.
  - Это и продуктовая история: edge-узел LinQ на площадке, оператор подключается к нему по сети.
- D-006 (24.10, локальная реализация) **Gateway получает JPEG конкретного analysis-кадра вместе с метаданными.**
  - Первоначальный вариант D-005 с независимым проигрыванием копии видео заменён: без общей capture identity оверлеи могли попадать на другой кадр после loop/reconnect.
  - Превью ограничено по частоте, размеру и сроку свежести; конкретные пределы заданы настройками и wire v1. Это выбранные ограничения, их пригодность для живого канала ещё не измерена.
  - События идут через транзакционный SQLite outbox и подтверждённый AMQP; краткоживущая телеметрия — отдельно. JPEG события переносится, клип остаётся на edge. Управление камерами пока выполняется на edge; gateway хранит решения оператора.
- D-007 (24.10, третий локальный пакет) **Удерживать весь пакет edge до commit, уведомлять после фиксации.** SQLite failure больше не означает потерю одноразового результата EventManager. Повторы используют тот же ID и readback, shutdown сохраняет ресурсы до очистки. Crash до первой durable записи при недоступном диске остаётся вне гарантии.
- D-008 (24.10, живой RabbitMQ 4.4) **Telemetry topology v2 с durable metadata очереди, TTL/max-length и временными сообщениями.** Новое имя `.telemetry.v2` позволяет избежать конфликта declaration с прежней non-durable очередью; deprecated feature брокера не включается, wire остаётся v1, чужие/старые очереди автоматически не удаляются.
- D-009 (24.10, CPU S1 baseline) **Сохранять исходный evaluator и явно считать strict precision с duplicate alarms.** Сопоставление start..confirmed и отсутствие actor GT ограничивают интерпретацию 3 TP/1 FN/1 duplicate; сначала уточнить непрерывность инцидентов/участников и clean-зоны, затем менять семантику или параметры.
- D-010 (24.10, приоритет моделей) **Сохранить YOLOv8n-640 по умолчанию.** На парных 600+600 кадрах n/s дали одинаковые 3 TP/1 FN/1 duplicate, но s требует в 2.71 раза больше video-loop времени. На одинаковых 141 размеченных изображениях person AP50 n/s 0.757/0.727. Это локальное сравнение, не универсальный рейтинг архитектур; пороги/tracker/evaluator не подгонялись.
- D-011 (24.10, PPE-кандидат) **Подключать PPE только opt-in, хранить unknown и отдельно оценивать отрицательные классы.** Core AP50 0.844 скрывает слабое сопоставление no_helmet (AP50 0.136, P/R 0.25/0.20 по исходному GT); GT no_vest отсутствует, respirator unsupported. Выявленные неоднородность рамок/пробелы публичного GT требуют надёжной целевой разметки. Не выводить отсутствие каски из отсутствия детекции и не снижать порог на test. Источники/веса/данные закреплены, training overlap неизвестен; до promotion нужны независимые целевые видео и оценка S2 событий.

- D-012 (24.10 13:00) **Дообучение на открытых наборах под слабые места.** Слабые места — S4 (погрузчик), S3 (лежащий человек), S7 (сигарета) и S2 (задержка каски, слабый no_helmet).
  - Почему:
    - разбор ошибок A9 (docs/QUALITY.md): 4 из 6 оставшихся пропусков — в моделях, а не в правилах;
    - готовая модель погрузчика (keremberke) путает фуры и экскаваторы с погрузчиком.
  - Как:
    - наборы из открытых источников (docs/DATASETS.md). Лицензии не проверяем — решение человека: демо внутреннее. Источники записываем;
    - честная оценка на отложенных данных: кадры 13 оценочных роликов и тесты наборов в обучение не входят;
    - сборка под TPU и сверка с CPU, карточка модели;
    - выкатка — только если по гейту не хуже.
- D-013 (24.10 13:00) **Маховик данных как часть продукта** (контракт docs/FLYWHEEL.md).
  - Как работает:
    - конвейер сам сохраняет сырые кадры: событий, неуверенных детекций, «мигающих» треков и расхождений TPU с CPU;
    - решение оператора превращает кадр в положительный пример или трудный негатив;
    - учитель (YOLOv8x, YOLO-World) предлагает разметку, человек принимает её одной клавишей;
    - дальше версия датасета → дообучение → TPU → гейт.
  - Без человека метки в обучение не идут: модель, которая учится на своих метках, закрепляет свои ошибки.
  - Почему: человек 24.10 в 12:16 спросил, можно ли расширить датасет или сделать механизм, который сам создаёт данные для обучения. Для экспертов это ответ на главное ограничение решения — мало данных.

- D-014 (24.10, объединение main) **Качество и внешний TPU — основной критерий.** CPU timings не служат запретом для тяжёлых кандидатов. Frozen CPU registry хранится отдельно от production TPU. Выбранный TPU backend без явного opt-in не переходит на полный CPU inference; отсутствие подключения/программы — наблюдаемая ошибка. CPU tail декодирования после TPU учитывается отдельно.
